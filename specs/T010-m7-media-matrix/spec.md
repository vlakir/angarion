## 1. Overview

M7 — финальный этап дорожной карты, замыкающий два обещания концепции.

**(A) Медиа.** До M7 событие несёт только факт наличия вложений
(`has_media: bool`), а метаданные доступны лишь через сырой `raw`. M7
вводит первоклассное представление вложений — `media: list[MediaRef]` в
событии — и **политику скачивания / хранения / пересылки** контента, чтобы
пайплайн мог не только знать о медиа, но и переносить его получателям и
отдавать процессорам. Изменение домена аддитивно (минорная версия, §17.8.2).

**(B) Matrix-адаптер.** Telegram пока единственный боевой адаптер, поэтому
тезис «замена мессенджера — это новый адаптер без изменения ядра» (§12.10)
ещё не доказан на практике. Matrix — кандидат №1 (единственный полный
аналог Telegram-профиля: личный аккаунт, правки через `m.replace`, удаления
через redactions, история через sync, self-hosted). Его реализация
**подтверждает переносимость портов** и впервые гоняет механизм управляемой
деградации по матрице возможностей на втором живом адаптере.

## 2. Сценарии использования

**Медиа:**

- Как пользователь библиотеки, я хочу, чтобы пайплайн пересылал получателям
  не только текст, но и приложенные фото/видео/документы исходного
  сообщения, чтобы зеркало/агрегатор был полноценным, а не текстовым огрызком.
- Как автор процессора, я хочу видеть структурированные метаданные вложений
  (тип, имя, размер, mime) и при необходимости получить локальный путь к
  скачанному файлу, чтобы обрабатывать контент (например, прогонять
  изображение через распознавание), а не только текст.
- Как оператор, я хочу управлять политикой медиа конфигом (скачивать ли,
  какие типы, лимит размера, куда складывать, сколько хранить), чтобы не
  забивать диск и не качать лишнего.

**Matrix:**

- Как пользователь библиотеки, я хочу подключить Matrix-комнаты как источники
  и/или получатели тем же способом, что и Telegram (секция `[accounts.*]`,
  пайплайны), чтобы переключение/добавление платформы не требовало правок ядра.
- Как мейнтейнер, я хочу, чтобы Matrix-адаптер декларировал свои возможности
  и проходил тот же контрактный набор портов (`angarion.testing`), что и
  Telegram, чтобы доказать переносимость и корректность деградации.

## 3. Functional Requirements

### 3.A. Медиа

**Домен и поток данных:**

- ДОЛЖНА: добавить в `InboundEvent` поле `media: list[MediaRef] | None`
  (аддитивно; `MediaRef` — новый доменный DTO на Pydantic, см. §5). Поле
  опционально: события без вложений — `None` или пустой список (выбор —
  Clarify).
- ДОЛЖНА: сохранить обратную совместимость по `has_media` (либо оставить
  поле, либо сделать вычисляемым из `media` — решение Clarify).
- ДОЛЖНА: переносить вложения через пайплайн на выход — встроенный
  `passthrough`-процессор ретранслирует медиа исходного события получателю
  (наряду с текстом). Способ доставки на send-стороне — §ниже.
- ДОЛЖНА: дать процессору доступ к метаданным вложений и (если скачано)
  к локальному контенту; шаблон/LLM-процессоры медиа не теряют при проходе
  (как минимум транзит, без обязательной обработки контента).

**Политика скачивания / хранения:**

- ДОЛЖНА: политика медиа задаётся конфигом (по аккаунту/пайплайну/глобально —
  уровень определяется в Clarify): скачивать ли вообще; whitelist/blacklist
  типов; лимит размера; целевой каталог хранения; ретеншн.
- ДОЛЖНА: по умолчанию **не скачивать** контент (только метаданные) — дёшево,
  безопасно, не упирается в лимиты/диск; скачивание — явный opt-in (выбор
  дефолта — Clarify).
- ДОЛЖНА: скачанные файлы складываются в git-ignored runtime-каталог (рядом
  с `data/`), путь конфигурируемый; ретеншн как у прочих данных (§17.3).
- НЕ ДОЛЖНА: ломать гарантии at-least-once/идемпотентности — повторная
  обработка/доставка медиа гасится теми же идемпотентными ключами выхода.

**Пересылка на send-стороне:**

- ДОЛЖНА: `OutboundMessage` несёт вложения для доставки (новое поле либо
  через `extra` — решение Clarify) так, чтобы `MessageSinkPort.send`
  передал их платформе.
- ДОЛЖНА: Telegram-sender умеет переотправить вложения. Предпочтительно —
  переиспользование платформенной ссылки (Telegram `file_id`/`InputMedia`)
  без повторной заливки в пределах того же аккаунта; для меж-аккаунтной/
  меж-платформенной доставки — через скачанный файл (требует включённого
  скачивания). Граница «когда нужен реальный байт-контент» — Clarify.

**Catch-up / реестр / дедуп:**

- ДОЛЖНА: определить, влияет ли изменение медиа (при неизменном тексте) на
  «изменилось ли содержимое» для catch-up/edit-детекции — сложить медиа-
  отпечаток в `content_hash` либо хранить отдельный media-хэш (решение
  Clarify). Текущий `content_hash` (`keys.py`) считается только по тексту.
- НЕ ДОЛЖНА: менять публичный формат ключей §7.2/§7.3 несовместимо (если
  media-хэш входит в дедуп — аддитивно и обоснованно в ADR).

### 3.B. Matrix-адаптер

- ДОЛЖНА: реализовать адаптер платформы `matrix` тем же plugin-контрактом
  (§12.11): пакет `src/angarion/adapters/matrix/`, объект `PLUGIN`
  (`AdapterPlugin`) с `name="matrix"`, `capabilities`, `account_config_model`,
  `make_listener`, `make_sender`; регистрация через entry point
  `angarion.adapters`. Optional extra: `angarion[matrix]`.
- ДОЛЖНА: декларировать возможности: `user_account=True`, `edit_events=True`
  (`m.replace`), `delete_events=True` (redactions), `history_fetch=True`
  (sync/`/messages`), `threads=True` (Matrix `m.thread` → `thread_id`),
  `push_transport="client"` (sync-loop, как Telethon).
- ДОЛЖНА: поддержать **шифрованные (E2EE) комнаты** (olm/megolm через
  `nio[e2e]`/`python-olm`): listener расшифровывает входящие, sender шлёт в
  зашифрованные комнаты. E2EE key-store ведёт `matrix-nio` (отдельный sqlite
  на ФС, git-ignored — см. §6); токен/`device_id` — в `app.db`.
- ДОЛЖНА: listener подключается к homeserver, делает catch-up по реестру и
  подписывается на live-события (sync-loop); эмитит `InboundEvent` через
  `IngestService` публичными хелперами ключей (§7.2). external_id =
  Matrix `event_id` (немонотонный — §302: домен не требует упорядоченности,
  семантикой позиции владеет адаптер).
- ДОЛЖНА: курсор источника непрозрачен — payload Matrix = sync-токен
  (`next_batch`) и/или позиция `/messages` (§9.2). Ядро курсор только хранит.
- ДОЛЖНА: маппить правки (`m.replace` relation → `MESSAGE_EDITED` с
  `previous_text` из реестра) и удаления (redaction → `MESSAGE_DELETED`).
- ДОЛЖНА: sender реализует `MessageSinkPort.send` — отправка в комнату
  (опц. в тред), `DeliveryReceipt` с `event_id`.
- ДОЛЖНА: account-config-модель `[accounts.<name>]` для Matrix: homeserver
  URL, user_id, device_id; первичная авторизация — парольный `angarion
  login`-аналог (обмен пароль → `access_token` + `device_id` + инициализация
  E2EE-стора); секреты — из env/интерактив, не в TOML (§17.7).
- ДОЛЖНА: проходить контрактные наборы `angarion.testing`, параметризованные
  своими capabilities (зелёный прогон = соответствие контракту, §12.11).
- ДОЛЖНА: на CI работать без живого homeserver — маппинг на зафиксированных
  фикстурах matrix-nio, как Telethon-маппинг на фикстурах (§13.2.1).
- ДОЛЖНА: поддержать медиа Matrix (`mxc://` вложения) в рамках Matrix-работы
  (часть B), а не откладывать аддитивом — `MediaRef` messenger-agnostic с
  части A (решение Clarify Q14: «сразу оба адаптера»).

### 3.C. Деградация и доказательство переносимости (сквозное)

- ДОЛЖНА: подтвердить на Matrix механизм §12.10 (если гипотетически
  `history_fetch=False` — catch-up отключается с предупреждением и событием
  `catchup_unavailable`; несовместимая конфигурация → fail-fast). Matrix
  полнопрофильный, поэтому деградация проверяется в т.ч. контрактным тестом
  на синтетическом адаптере с урезанными capabilities (если ещё не покрыто).
- ДОЛЖНА: матрица возможностей обоих адаптеров видна в `/ui/diagnostics`
  (механизм есть с M5 — проверить, что Matrix туда попадает).

## 4. Success Criteria

**Медиа:**

- Событие с вложением несёт структурированный `media: list[MediaRef]` с
  типом/именем/размером/mime; `passthrough` пересылает медиа получателю.
- При включённом скачивании файл оказывается в конфигурируемом каталоге,
  доступен процессору по локальному пути; при выключенном — только метаданные.
- Telegram end-to-end: фото/видео/документ из источника доходит в цель
  (продемонстрировано примером в `examples/` и/или интеграционным тестом).
- Дедуп/catch-up корректен при изменении медиа (поведение зафиксировано
  тестом согласно решению Clarify по media-хэшу).

**Matrix:**

- Matrix-адаптер загружается как плагин; пайплайн Matrix-источник →
  Matrix-цель (и/или кросс: Telegram↔Matrix) работает: new/edited/deleted.
- Контрактные наборы портов (`angarion.testing`) зелёные для Matrix-маппинга
  на фикстурах; catch-up по sync-токену покрыт на синтетической истории.
- Деградация по матрице возможностей подтверждена тестом.

**Общее:**

- Четыре pre-push проверки (ruff check / ruff format --check / mypy --strict /
  pytest) — 0 ошибок; coverage ≥ 90% держится.
- README roadmap M7 ✅; `CHANGELOG.md`, `DECISIONS.md` обновлены; примеры
  в `examples/` для user-facing частей (медиа-пересылка, Matrix-пайплайн).

## 5. Key Entities

- **`MediaRef`** (новый доменный DTO, Pydantic) — концептуальные поля
  (финал — Implement/Clarify): `kind` (photo/video/document/audio/voice/
  sticker/…; открытый/закрытый enum — Clarify), платформенная непрозрачная
  ссылка (`file_id`-аналог), `mime_type`, `file_name`, `size`, опц.
  размеры/длительность, флаг «скачано» + локальный путь/URL, опц. media-хэш.
- **Политика медиа** (конфиг) — `download` (bool/enum), `allowed_kinds`,
  `max_size`, `storage_dir`, `retention` — уровень (account/pipeline/global)
  определяется в Clarify.
- **Matrix `AdapterPlugin`** — `PLUGIN` в `adapters/matrix/plugin.py`:
  capabilities, `MatrixAccountConfig` (homeserver/идентификация/device),
  `make_listener` (sync-loop + catch-up), `make_sender`.
- **Matrix-курсор** — непрозрачный payload с `next_batch`/позицией истории.
- **`MediaStorePort`?** — возможный новый порт хранения блобов, либо просто
  файловый каталог без порта (решение Clarify).

## 6. Assumptions & Constraints

- Медиа-изменение домена **аддитивно** и заранее санкционировано (§17.8.2):
  не требует ревизии ТЗ.
- Скачивание медиа упирается в лимиты платформы и диск → по умолчанию
  консервативно (метаданные без контента), скачивание — opt-in.
- Matrix-клиент — `matrix-nio` (де-факто стандарт), extra `angarion[matrix]`;
  для E2EE — `nio[e2e]` (тянет `python-olm`). Синхронные части изолируются в
  адаптере (`to_thread`), ядро остаётся asyncio.
- E2EE key-store `matrix-nio` — отдельный sqlite на ФС (git-ignored каталог,
  как `data/`); библиотека ведёт его сама. В `app.db` — только `access_token`
  + `device_id` (`SessionStorePort`). Единственное отступление от «вся сессия
  в app.db» (Telegram ADR 2026-06-13); зафиксировать в бэкап-гайде §17.6.
- Matrix `event_id` немонотонен; упорядочивание/позиция — забота адаптера
  (§302, §9.2); курсор непрозрачен для ядра.
- Интеграционные тесты Matrix требуют homeserver/аккаунт (как Telegram-контур
  M6 требует реальный аккаунт) → по маркеру `integration`, default-skip;
  обязательный CI — на фикстурах.
- Один worker на пайплайн (§17.8.1) — медиа не меняет модель параллелизма.

## 7. Out of Scope

- Третий+ мессенджер (MAX, VK, Discord — §12.10) — последующие отдельные
  задачи, вне M7.
- Обработка/трансформация медиа-контента процессорами (распознавание,
  транскодирование) — M7 даёт транзит + доступ к файлу; конкретные
  AI-обработчики медиа — отдельные примеры/процессоры (ср. T020).
- Редактирование уже отправленного медиа на стороне получателя (edit media):
  оценивается отдельно; M7 фокус — new + текстовые edit/delete + транзит медиа.
- Стриминг/чанкование очень больших файлов сверх лимита платформы.
- Заморозка публичного API / релиз 1.0 — отдельное решение, не в M7.
- S3/удалённое медиа-хранилище (`MediaStorePort`), AI-обработка контента —
  последующие аддитивы.

## Clarify (заполняется Claude — встречный диалог с Владимиром)

### Open questions

**Медиа:**

1. **`media` пустое — `None` или `[]`?** Единообразие с `has_media`: оставляем
   `has_media` отдельным полем для обратной совместимости или делаем его
   `@computed_field` от `media`? (Влияет на публичный API события.)
2. **Дефолт скачивания.** Подтверждаешь консервативный дефолт «не скачивать,
   только метаданные», скачивание — явный opt-in конфигом? Или для целевого
   сценария (зеркало с медиа) удобнее дефолт «скачивать для пересылки»?
3. **Уровень политики медиа.** Глобально, по аккаунту, по пайплайну — или
   несколько уровней с переопределением? (Зеркало хочет пересылать медиа в
   одном пайплайне и игнорировать в другом — намекает на pipeline-уровень.)
4. **Пересылка без скачивания.** Для Telegram→тот же аккаунт можно
   переотправлять по `file_id`/`InputMedia` без скачивания. Делаем этот
   быстрый путь основным (скачивание только когда нужен реальный байт-контент:
   кросс-аккаунт/кросс-платформа/обработка)? Это снимает «по умолчанию диск
   не растёт» и одновременно даёт пересылку медиа из коробки.
5. **Media-хэш и дедуп/edit.** Если у сообщения изменилось только вложение
   (текст тот же) — это `MESSAGE_EDITED`? Складывать медиа-отпечаток в
   `content_hash` (тогда смена медиа = edit) или хранить отдельно и не считать
   edit'ом? (Затрагивает catch-up-сверку и формат дедуп-ключа §7.2.)
6. **Новый порт хранения медиа?** Хватит файлового каталога с политикой, или
   нужен `MediaStorePort` (абстракция хранилища: ФС/S3/…)? Для v1 предлагаю
   файловый каталог без порта (проще, S3 — позже аддитивом). Согласен?
7. **Набор типов `MediaRef.kind`.** Открытый `str` (как `Messenger`) или
   закрытый enum фиксированных типов? Открытый дружелюбнее к новым платформам.

**Matrix:**

8. **Клиентская библиотека.** `matrix-nio` (async, де-факто стандарт) —
   утверждаем как зависимость extra `angarion[matrix]`? Альтернативы знаешь/
   предпочитаешь?
9. **Идентификация аккаунта.** Поддерживаем вход по `access_token` (+ user_id,
   device_id) — без хранения пароля; или нужен и парольный логин (как
   `angarion login` у Telegram) с обменом на токен? Токен проще и безопаснее;
   пароль удобнее для первого входа. Что в v1?
10. **Хранение сессии Matrix.** Telegram-сессия живёт в `app.db` (ADR
    2026-06-13). Matrix `access_token`/`device_id`/ключи — туда же (в
    `SessionStorePort`), или из env/конфига? (E2EE-комнаты потребуют хранить
    ключи устройства — см. ниже.)
11. **E2EE-комнаты.** Поддерживаем шифрованные Matrix-комнаты в v1 (нужен
    olm/megolm, хранение ключей, верификация устройств — заметный объём) или
    **только незашифрованные** комнаты в M7, E2EE — отдельной задачей? Сильно
    влияет на объём.
12. **Threads.** Matrix-треды (`m.thread`) маппим в `thread_id` (capability
    `threads=True`) сразу, или `threads=False` в v1 (только основной таймлайн
    комнаты)?
13. **Интеграционный контур Matrix.** Есть ли у тебя доступный homeserver
    (matrix.org аккаунт / self-hosted Synapse/Conduit / dev-контейнер) для
    интеграционного маркера, или ограничиваемся фикстурами + примером без
    живого прогона на этапе M7?

**Состав/последовательность:**

## Analyze (Claude, 2026-06-16)

**Медиа:**

- 🟡 **`content_hash` теперь зависит от медиа (Q5) — миграция реестра.**
  Записи реестра, записанные до M7, имеют text-only `content_hash`. После
  смены формулы хэш «того же» сообщения изменится → первый post-M7 catch-up
  может ложно счесть старые сообщения отредактированными (всплеск ложных
  `MESSAGE_EDITED`). Решение на Implement (A3): либо версионировать формулу
  хэша и пересчитывать лениво, либо включать медиа-отпечаток **отдельным**
  полем реестра, оставив text-`content_hash` неизменным, а edit-детекцию
  делать по `(content_hash, media_hash)`. Второй вариант безопаснее для
  совместимости — фиксирую как предпочтительный, финал в ADR A3.
- 🟡 **Идемпотентность выхода и fast-path reupload.** Идемпотентный ключ
  выхода строится сейчас по тексту/событию; при пересылке медиа без текста
  (только фото) `text` пуст → ключ должен включать медиа-идентичность, иначе
  два разных фото в одном диалоге могут коллидировать по ключу. Проверить
  построение `idempotency_key` в A1.
- 🟢 **`passthrough` с `text=None`, но с медиа.** Сейчас `passthrough` дропает
  событие при `text=None` (удаление). Теперь «нет текста, но есть медиа» —
  валидный кейс доставки: правило дропа уточнить (дропаем только когда нет ни
  текста, ни медиа). A1.
- 🟢 **Fast-path и сроки жизни ссылок.** Telegram `file_id` валиден для
  переотправки тем же аккаунтом; на кросс-аккаунт/кросс-платформу падаем в
  скачивание. Матрица «когда нужен байт-контент» — таблица в A2/B3.
- 🟢 **Ретеншн скачанных файлов** подключается к существующему prune-механизму
  (§17.3), без отдельной подсистемы. A3.

**Matrix:**

- 🔴 **E2EE существенно расширяет объём части B.** olm/megolm, персистентный
  key-store, ротация/проблема «unable to decrypt» (UTD) при отсутствии ключей
  сессии до момента входа устройства, верификация устройств. Для зеркала
  верификация устройств может быть выключена (trust-on-first-use / игнор
  непроверенных), но UTD для исторических сообщений до создания device —
  фундаментальное ограничение Matrix E2EE (не баг адаптера): catch-up по
  зашифрованной истории **до** первого логина устройства недоступен. Зафик-
  сировать как platform limitation (§9.4-аналог, реестр ограничений §17.9) и
  покрыть тестом «UTD → событие пропускается с пометкой, не падение». B-фаза.
- 🟡 **Курсор Matrix: sync-токен vs история.** Live идёт по `next_batch`
  (sync), catch-up истории — по `/messages` с `from`-токеном (prev_batch).
  Это две разные позиции; непрозрачный payload курсора должен нести обе
  (или адаптер сам решает, что положить). Семантикой владеет адаптер (§9.2) —
  упущения в FR нет, но в B2 спроектировать payload явно.
- 🟡 **Немонотонный `event_id` и edit/delete по реестру.** `previous_text`
  для `m.replace` берётся из реестра по `external_id` целевого события
  (`m.relates_to`/`event_id`). Redaction несёт `redacts: event_id`. Маппинг
  опирается на реестр — на CI это покрывается фикстурами + синтетической
  историей (как Telethon). Контрактный набор catch-up параметризовать
  Matrix-историей.
- 🟢 **Деградация по матрице.** Matrix полнопрофилен (всё `True`), поэтому
  сам по себе деградацию не провоцирует. Тест деградации — на синтетическом
  адаптере с урезанными capabilities (проверить, не покрыто ли уже с M1);
  если покрыто — переиспользовать, новый не плодить. C-сквозное.
- 🟢 **`threads=True` и `thread_id` в реестре/ключах.** `thread_id` уже в
  `Address` и хелперах ключей с M1 — Matrix-треды ложатся на существующий
  механизм без изменения портов.

**Сквозное:**

- 🟢 **Объём M7 большой, но фазируется.** Часть A (медиа, ~4 фазы) и часть B
  (Matrix+E2EE, ~4–5 фаз) независимы; каждая фаза — отдельный PR под T010.
  WIP-лимит соблюдаем: в `Doing` — одна фаза за раз.
- 🟢 **Coverage ≥ 90% и `mypy --strict`.** E2EE/медиа-ветки с внешним I/O
  изолировать за портами/адаптерными границами, чтобы держать покрытие
  доменной/application-логики; адаптерный I/O — на фикстурах.
