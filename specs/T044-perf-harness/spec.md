# Spec: Нагрузочный гарнес — пропускная способность и узкие места (T044)

**Статус:** Analyzed
**Дата создания:** 2026-06-20
**Связанные документы:** CONCEPT.md §17.5 (мониторинг глубины очереди),
§17.8 (санкционированная эволюция: конкурентность воркеров); DECISIONS.md
(M1 «конкурентность = 1, единичный worker даёт строгий FIFO бесплатно»).

---

## 1. Overview

Инструмент нагрузочного тестирования angarion: прогоняет через
приложение синтетический поток записей без реальных платформ и измеряет
**реальную нагрузочную способность** (сколько records/sec тянет
конвейер целиком) и **узкие места** (какой компонент сериализует поток).
Нужен, чтобы (а) задокументировать baseline текущей однопоточной
M1-архитектуры цифрами, а не «на глаз», и (б) подготовить
доказательную почву для будущего решения о конкурентности воркеров
(§17.8) — где именно параллелить и сколько это даст.

Форма — perf-тесты в `tests/perf/` (pytest-based), отделённые от
основного gated-прогона. Не часть публичного API библиотеки —
dev/infra-инструмент.

## 2. Сценарии использования

<!-- Инфраструктурный инструмент: пользователей нет, есть сценарии. -->

- Разработчик запускает perf-прогон на своей машине и получает отчёт:
  throughput (rec/s), латентность p50/p95/p99, пиковая глубина очереди,
  атрибуция времени по компонентам — для двух конфигураций бэкендов
  (memory-потолок и persistqueue+SQLite-реалистично).
- Разработчик сравнивает memory- и sqlite-прогоны, чтобы увидеть «цену
  персистентности» и локализовать сериализующую точку (write-lock
  SQLite / per-event INSERT аналитики / poll-delivery / отсутствие
  батчинга на queue.get).
- При обсуждении §17.8 (конкурентность) разработчик опирается на
  измеренный baseline и список узких мест, а не на догадки.
- (Опционально, при включённом soft-пороге) прогон сигналит, если
  throughput просел ниже зафиксированной планки — лёгкий
  regression-сигнал, не CI-гейт по умолчанию.

## 3. Functional Requirements

- ДОЛЖНА: гонять полный сквозной путь `ingest → queue → worker →
  delivery` на синтетическом транспорте без сети (MemoryListener →
  MemorySink / counting-sink), с тривиальным процессором (измеряем
  накладные расходы фреймворка, а не стоимость обработки).
- ДОЛЖНА: измерять **end-to-end throughput** (rec/s) на фиксированном
  пакете из N записей (closed-loop: подать N, дождаться обработки всех,
  поделить на затраченное время).
- ДОЛЖНА: измерять **латентность p50/p95/p99** на запись (ingest →
  delivered).
- ДОЛЖНА: прогонять **обе матрицы бэкендов** — (1) memory queue +
  memory storage = теоретический потолок; (2) persistqueue + SQLite
  storage = реалистичная ёмкость.
- ДОЛЖНА: измерять **насыщение / backpressure** — поведение под
  устойчивой нагрузкой: рост `queue.depth()` во времени, удержание
  целевого темпа подачи, точка, где обработка перестаёт успевать.
- ДОЛЖНА: давать **изоляцию узких мест** методом (a)+(b)+(c):
  (a) компонентные микро-бенчи портов в изоляции (цикл queue.put/get,
  analytics.record, dedup/registry/outbox) → rec/s каждого; (b) сквозная
  атрибуция времени по этапам; (c) сэмплирующий профайлер
  (`pyinstrument`, dev-dep) на sqlite-прогоне — указать сериализующую
  точку, а не только общий потолок.
- ДОЛЖНА: реализовать **обе формы нагрузки** — closed-loop burst
  фиксированного N (для throughput/латентности) и sustained/ramp с
  целевым темпом (для насыщения/backpressure). Дефолты (burst 10k,
  sustained 30s) настраиваемы через env/параметр.
- МОЖЕТ: **прототип конкурентного воркера за флагом** (по умолчанию
  ВЫКЛЮЧЕН — дефолт остаётся строгим M1/FIFO) + замер прироста
  throughput против baseline. Включение прототипа меняет семантику
  порядка → обязателен ADR в `DECISIONS.md`.
- ДОЛЖНА: печатать человекочитаемый отчёт по каждому прогону (числа +
  конфигурация прогона: бэкенды, N, knobs воркера).
- ДОЛЖНА: быть воспроизводимой и детерминированной по составу
  (фиксированный seed/набор входных записей; числа — машинозависимы).
- ДОЛЖНА: поддерживать опциональный soft-порог через переменную
  окружения (напр. `ANGARION_PERF_MIN_RPS`, по умолчанию ВЫКЛЮЧЕН) —
  если задан и throughput ниже, perf-тест падает; лёгкий
  regression-сигнал по желанию.
- МОЖЕТ: сохранять отчёт в файл-артефакт (JSON) для сравнения прогонов.
- НЕ ДОЛЖНА: входить в gated-прогон `uv run pytest` (четыре pre-push
  проверки) — машинозависимый абсолютный throughput сделает гейт
  flaky; perf-тесты собираются/гоняются отдельным маркером
  (`@pytest.mark.perf`, `addopts = -m "not perf"`), исключены из
  coverage на `src/`.
- НЕ ДОЛЖНА: бить по реальным платформам (Telegram/Matrix) или сети.
- НЕ ДОЛЖНА: менять дефолтное поведение M1 — прототип конкурентности
  только за флагом, по умолчанию выключен, строгий FIFO сохраняется.

## 4. Success Criteria

- Один прогон выдаёт по каждой из двух конфигураций: throughput (rec/s),
  латентность p50/p95/p99 (мс), пиковую/финальную глубину очереди, и
  атрибуцию по компонентам — в виде отчёта.
- Контраст memory-vs-sqlite измерен и зафиксирован числом («цена
  персистентности» в rec/s и по латентности).
- Узкое место sqlite-конфигурации названо и подтверждено
  доказательством (компонентная атрибуция / профиль), а не заявлено
  умозрительно.
- Результаты и выводы (baseline + узкие места + замечание про §17.8)
  занесены в `CHANGELOG.md` и, при архитектурной значимости, в
  `DECISIONS.md`.
- Perf-тесты не влияют на зелёность четырёх pre-push проверок
  (исключены из gated-прогона и из coverage на `src/`).
- Прогон воспроизводим командой из README/доков perf-гарнеса.

## 5. Key Entities

- **Загрузочный профиль (load profile):** N записей, темп подачи
  (burst / целевой rate), форма (closed-loop burst vs sustained ramp).
- **Конфигурация прогона (run config):** комбинация бэкендов (memory /
  sqlite), knobs воркера (poll_interval, max_retries, batch-параметры),
  процессор (тривиальный).
- **Замер (measurement):** на запись — временные метки этапов
  (ingest / processed / delivered); агрегаты — throughput, перцентили
  латентности, профиль глубины очереди.
- **Отчёт (report):** сводка чисел + конфигурация прогона; печать в
  stdout, опционально JSON-артефакт.
- **Counting/Null sink:** сток, который считает доставленное, не
  накапливая список (для больших/устойчивых прогонов вместо
  растущего `MemorySink.sent`).

## 6. Assumptions & Constraints

- Минимальная версия Python — 3.12; стек `uv` + `pytest` +
  `pytest-asyncio`.
- Существующий синтетический контур (MemoryListener → ingest → queue →
  worker → delivery → MemorySink) пригоден как ядро гарнеса; то же
  крутят e2e-тесты (`tests/e2e/`, `tests/integration/harness.py`).
- Абсолютные числа машинозависимы (CPU, диск, FS) — гарнес печатает
  числа и условия прогона; кросс-машинное сравнение не гарантируется.
- SQLite-конфигурация имеет известные сериализующие точки: единый
  write-lock (dedup / registry / outbox / analytics — каждое событие
  отдельной транзакцией с retry-on-locked), poll-based delivery
  (`due(limit=1)`, `poll_interval` по умолчанию 1.0s), отсутствие
  батчинга на `queue.get()`.
- Текущая обработка однопоточна (M1: один PipelineWorker, один
  DeliveryWorker, один OutboxConsumer) — это и есть измеряемый baseline.

## 7. Out of Scope

- Production-grade конкурентность / батчинг очереди / батч-INSERT
  аналитики (§17.8) — T044 даёт только flag-gated **прототип** +
  измерение прироста; доведение до продакшена (надёжность, retry под
  параллелизмом, hardening) — отдельная будущая задача.
- Нагрузка по реальным платформам (Telegram/Matrix) и сетевые
  бенчмарки.
- Кросс-машинные/CI-абсолютные SLA и жёсткие пороги-гейты в основном
  прогоне.
- Бенчмарк конкретных «тяжёлых» процессоров (LLM и т.п.) — измеряем
  накладные расходы фреймворка на тривиальном процессоре.
- Публичный API для нагрузочного тестирования — это dev-инструмент.

**Detail-clarify (2026-06-20):**

1. **Изоляция узких мест** — метод (a)+(b)+(c): компонентные
   микро-бенчи портов + сквозная атрибуция по этапам + сэмплирующий

   `pyinstrument` требует мини-ADR.
2. **Тайминги латентности** — собственные `perf_counter`-метки в
   гарнесе (монотонные); `AnalyticsEvent.at` — как кросс-проверка.
   *(дефолт Claude, подтверждён без возражений)*
3. **Пороги** — характеризация (измеряем+печатаем) + опциональный
   soft-порог через env `ANGARION_PERF_MIN_RPS` (по умолчанию выключен)
   как regression-сигнал. Жёстких порогов-гейтов нет.
4. **Counting/Null-сток** — в `angarion.testing` (переиспользуемо,
   рядом с фейками/контрактами). *(дефолт Claude, подтверждён)*
5. **Формы нагрузки** — обе: closed-loop burst фикс. N + sustained/ramp
   с целевым темпом. Дефолты burst 10k / sustained 30s, настраиваемы.
6. **Граница §17.8** — **расширена против исходного черновика**: T044
   включает flag-gated **прототип** конкурентного воркера + замер
   прироста (а не только измерение baseline). Прототип по умолчанию
   выключен (дефолт = строгий M1/FIFO); смена семантики порядка →
   обязателен ADR. Доведение конкурентности до продакшена — отдельная
   задача.
7. **Coverage-гейт** — маркер `@pytest.mark.perf` + `addopts = -m "not
   perf"`; perf-тесты не собираются обычным прогоном и не влияют на
   `--cov-fail-under=90`. *(дефолт Claude, подтверждён)*

### ADR-долги (внести в DECISIONS.md при реализации)

- **ADR: dev-зависимость `pyinstrument`** — зачем сэмплирующий
  профайлер, почему он dev-only и не тянется в рантайм-зависимости.
- **ADR: flag-gated конкурентный воркер** — допускаем потерю строгого
  FIFO ради throughput ТОЛЬКО за флагом (по умолчанию выключен);
  рассмотренные альтернативы (батчинг очереди, батч-INSERT аналитики,
  пул consumer'ов), ожидаемый потолок, что остаётся за рамками
  прототипа.

## Analyze (заполняется Claude)

Перечитаны spec + plan; проверены опорные факты по коду
(`adapters/memory/listener.py:59`, `domain/models.py:203,244`,
`adapters/memory/sink.py`).

- 🟡 **Латентность зависит от `OutboundRecord.record_uid` (Optional).**
  Корреляция «доставлено → исходная запись» идёт по `record_uid`, а он
  `UUID | None`. На тривиальном `passthrough`-процессоре он должен быть
  заполнен — проверить в фазе A; если процессор его не проставляет,
  гарнес считает латентность некорректно. Запасной путь — стартовую и
  конечную метки класть по `external_id` входной записи.
- 🟡 **`delivery.poll_interval` по умолчанию 1.0s доминирует над
  throughput.** Гарнес ОБЯЗАН уменьшать poll_interval (и минимизировать
  retry-backoff), иначе меряем `asyncio.sleep`, а не конвейер.
  Зафиксировано в Assumptions; вынести в обязательный шаг сборки app.
- 🟡 **sqlite-прогоны конкурируют за один write-lock между `queue.db`
  и `app.db`.** Это и есть предмет измерения, но каждый perf-тест
  обязан работать на изолированном `tmp_path` и чистить файлы, иначе
  прогоны влияют друг на друга и числа «плывут».
- 🟡 **Место флага конкурентности (фаза D) не зафиксировано.** harness-
  local параллельный драйвер vs реальный `[worker].concurrency` в
  `src/` — разные по влиянию на ядро. Решается мини-спекой перед фазой
  D (отмечено в plan.md). Не блокирует фазы A–C.
- 🟢 **counting-sink в `angarion.testing` — публичная поверхность.**
  Добавляем в тестовый namespace осознанно (переиспользуемо
  контрактно); не часть рантайм-API библиотеки.
- 🟢 **Абсолютные числа машинозависимы.** Принято: гарнес печатает
  числа + условия прогона; кросс-машинных SLA нет (Out of Scope).
- 🟢 **Чистый проход:** критических (🔴) противоречий не найдено;
  фазы A–C можно начинать, D — после мини-спеки по месту флага.
