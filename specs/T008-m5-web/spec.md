## 1. Overview

M5 даёт `angarion` **человеко- и машино-ориентированный фронт**: FastAPI
как второй driving-адаптер (симметричный Telethon-listener'у), web-дашборд
для наблюдения и управления, аутентификацию с ролями и саморегистрацией,
динамические настройки «на лету» и мост между процессами (командный
outbox). До этого этапа библиотека управлялась только из CLI и
конфиг-файла; M5 превращает её в наблюдаемый и администрируемый сервис,
не нарушая гексагональную дисциплину — весь web-слой общается с системой
**только через порты**. Завершение M5 — рубеж **1.0.0** (с этого момента
действуют гарантии стабильности публичного API §12.11).

## 2. Сценарии использования

- Как **оператор**, я хочу открыть `/ui` и видеть живой дашборд (глубина
  очереди, события за 24 ч по видам, состояние курсоров, таблица
  пайплайнов) с автообновлением — чтобы понимать состояние системы без
  чтения логов.
- Как **оператор**, я хочу на `/ui/pipelines` видеть граф «источники →
  пайплайны → получатели» с цветовым статусом и метриками — чтобы
  визуально оценить топологию и здоровье.
- Как **админ**, я хочу из браузера ставить пайплайн на паузу и снимать
  с паузы, делать requeue из DLQ, запускать ручной catch-up и
  перезапуск — **без потери событий и без SSH** — чтобы рутинная
  эксплуатация шла через UI.
- Как **админ**, я хочу одобрять заявки на регистрацию и управлять
  пользователями (роль, деактивация, удаление) через `/ui/users` — чтобы
  раздавать доступ без правки файлов.
- Как **новый пользователь**, я хочу самостоятельно зарегистрироваться и
  дождаться одобрения админа — чтобы получить доступ к наблюдению.
- Как **админ**, я хочу при создании заявки получать уведомление в
  Telegram (через сам же механизм доставки библиотеки) — чтобы не
  опрашивать список заявок вручную.
- Как **автор интеграции**, я хочу добавлять собственные JSON-ручки и
  UI-страницы поверх опубликованных DI-зависимостей и layout — чтобы
  расширять диагностику, оставаясь в рамках портов.
- Как **оператор большой нагрузки**, я хочу запускать api отдельным
  процессом (`--role api`) от pipeline-процесса — чтобы web-трафик не
  делил event-loop с ingest/worker.

## 3. Functional Requirements

Сгруппировано по разделам ТЗ. Технические детали — в соответствующих
§ CONCEPT; здесь — что система **должна** уметь.

### FR-0. Bootstrap-валидация (fail-fast; вкл. свёрнутый T021)
- ДОЛЖНА: на старте роли с включённым api при пустой таблице
  пользователей создавать админа из env `ANGARION_ADMIN_LOGIN` /
  `ANGARION_ADMIN_PASSWORD`; при `auth="users"` и отсутствии env —
  **fail-fast** с внятным сообщением (§12.7).
- ДОЛЖНА: при `auth="users"` требовать `ANGARION_API__SECRET` (env),
  иначе **fail-fast** (§12.7).
- ДОЛЖНА (T021): валидировать `processor_config` каждого процессора на
  старте (`build_app`), до приёма событий, через хук `config_model` в
  контракте `ProcessorPort` (по образцу `account_config_model`
  адаптера §12.11). Невалидный конфиг → `ConfigError` при старте, а не
  на первом событии.
- ДОЛЖНА: при `auth="none"` и bind не на `127.0.0.1` писать громкое
  предупреждение в лог при старте (§12.7).

### FR-1. Web API (§12.5)
- ДОЛЖНА: предоставлять фабрику `create_app(deps, *, routers, pages,
  title)`, кладущую контейнер портов `AngarionDeps` в `app.state`.
- ДОЛЖНА: публиковать типизированные FastAPI-зависимости поверх портов
  (`AnalyticsDep`, `RegistryDep`, `StateDep`, `QueueDep`, `CursorsDep`)
  как **публичный API** для пользовательских ручек.
- ДОЛЖНА: отдавать встроенный read-only роутер `/api/v1`:
  `GET /health` (без портов), `GET /diagnostics`, `GET /events`.
- ДОЛЖНА: монтировать пользовательские webhook-роутеры адаптеров
  (push_transport=webhook, §15.18 / ADR M5) при bootstrap.
- НЕ ДОЛЖНА: пропускать ORM-сущности, сессии SQLAlchemy и объекты
  Telethon в HTTP-слой; write-ручки, кроме управления пользователями
  (§12.7) и админ-операций (§12.8), — вне рамок v1.

### FR-2. Web UI (§12.6)
- ДОЛЖНА: рендерить SSR-дашборд на Jinja2 + htmx + Pico.css **без Node
  и сборки**; ассеты (htmx, pico) — в пакете, отдаются через
  `StaticFiles` (офлайн-режим, без CDN).
- ДОЛЖНА: давать страницы `/ui` (дашборд), `/ui/events` (журнал с
  фильтрами), `/ui/fragments/*` (партиалы для htmx-поллинга).
- ДОЛЖНА: давать `/ui/pipelines` — трёхдольный граф, **SVG генерируется
  на сервере** Jinja-шаблоном (без графических JS-библиотек); цвет узла
  пайплайна = статус (активен / пауза / есть failed за час); аннотации
  delivered/depth; клик по узлу (admin) — htmx-форма pause/resume.
- ДОЛЖНА: публиковать контракт расширения — базовый layout
  `angarion/base.html`, `ChoiceLoader` для пользовательских шаблонов,
  `register_page(title, path, router)` с автопоявлением в навигации.
- НЕ ДОЛЖНА: давать прямой доступ к ORM из шаблонного слоя; редактировать
  топологию пайплайнов через UI (топология статична, §12.8).

### FR-3. Аутентификация и авторизация (§12.7)
- ДОЛЖНА: строиться на **fastapi-users** + `fastapi-users-db-sqlalchemy`;
  `UserRow` — ORM-сущность, схема — миграцией Alembic.
- ДОЛЖНА: поддерживать два транспорта над одним user store: **JWT
  (Bearer)** для `/api/v1/*` и **HTTPOnly-cookie** для `/ui/*`.
- ДОЛЖНА: роли v1 — `admin` и `viewer`; встроенная диагностика доступна
  обеим, write (управление пользователями, админ-операции) — только
  admin.
- ДОЛЖНА: саморегистрация (`/ui/register`, `POST /api/v1/auth/register`)
  создаёт `is_active=false`; вход возможен только после одобрения админом
  в `/ui/users` (назначение роли, по умолчанию `viewer`).
- ДОЛЖНА: защищать от замусоривания — лимит `max_pending_registrations`
  (default 20); `registration_enabled=false` отключает саморегистрацию
  целиком.
- ДОЛЖНА: навешивать авторизацию **на уровне роутеров**; публичные
  исключения: `health`, `auth/login`, `auth/register`, `/ui/login`,
  `/ui/register`, `/ui/static/*`.
- ДОЛЖНА: экспортировать зависимости `CurrentUser`, `AdminUser` как
  публичный API; пользовательские роутеры по умолчанию закрыты
  `CurrentUser`, открытость — осознанный `public=True`.
- МОЖЕТ: работать в режиме `auth="none"` (dev / строго локальный запуск).
- CLI `angarion user ...` — только **аварийный fallback**, не основной
  инструмент.

### FR-4. Динамические настройки и админ-операции (§12.8)
- ДОЛЖНА: разделять статические (TOML+env, в UI read-only, секреты
  маскируются) и динамические (БД поверх файла, без перезапуска)
  настройки.
- ДОЛЖНА: вводить DTO `DynamicSettings` (Pydantic) + порт
  `RuntimeConfigPort` (`load()`, `save(patch)`); реализации —
  SQLAlchemy (`AppSettingRow`, key-value JSON) + InMemory.
- ДОЛЖНА: приоритет БД-override над файлом; «сброс к файлу» = удаление
  override'а.
- ДОЛЖНА: применять динамику на лету — компоненты читают
  `RuntimeConfigPort` в начале итерации (пауза пайплайна в worker,
  лимиты троттлинга sender'а) либо по in-process событию
  `settings_changed` (log level).
- ДОЛЖНА: **пауза ≠ потеря**: ingest продолжает класть в очередь, worker
  откладывает envelope'ы приостановленного пайплайна (возврат в хвост с
  задержкой, событие `deferred`); возобновление обрабатывает накопленное.
- ДОЛЖНА: давать `/ui/settings` (admin): зона «Конфигурация» (read-only,
  секреты маскированы) + зона «Управление» (формы динамики с пометкой
  источника файл/override).
- ДОЛЖНА: админ-операции (admin): restart, pause/resume пайплайна,
  requeue DLQ (с `attempt=0`, `requeued_at`; `/ui/dlq`), ручной catch-up.
- ДОЛЖНА: писать **аудит** — каждая операция и каждое изменение динамики
  → событие `admin_op` (пользователь, операция, старое/новое) в
  аналитику, видно в `/ui/events`; подтверждение в UI для разрушительных.

### FR-5. Командный outbox и роли процессов (§12.9, §16 #15)
- ДОЛЖНА: вводить `OutboxCommandRow` (ORM) + порт `CommandOutboxPort`;
  реализации SQLAlchemy + InMemory.
- ДОЛЖНА: producer — api-процесс (и application в комбинированном
  режиме); consumer — pipeline-процесс (фоновый поллинг
  `outbox_poll_seconds`, default 5), исполняет, помечает done/failed.
- ДОЛЖНА: семантика at-least-once с защитой по статусу — атомарное
  взятие `UPDATE ... WHERE status='pending'` (rowcount).
- ДОЛЖНА: виды команд v1 — `notify` (через `MessageSinkPort`), `catchup`
  (source_key), `restart_pipeline` (graceful shutdown pipeline-процесса);
  расширение = новый вид без изменения механизма.
- ДОЛЖНА: уведомление о заявке (§12.7) — **неблокирующее**: сбой
  исполнения логируется + `notify_failed` в аналитику, на регистрацию не
  влияет.
- ДОЛЖНА: поддерживать режимы запуска — встроенный (`angarion run
  --with-api`, uvicorn как asyncio-задача) и раздельный (`--role
  pipeline` + `--role api`); ingest и worker **не разделяются** на
  процессы (общие Telethon-клиенты, ограничение сессий §12.1).
- В комбинированном режиме механизм outbox тот же (producer+consumer в
  одном процессе) — поведение и тесты едины.

## 4. Success Criteria

Из §16 M5 (acceptance — ASGI-тесты зелёные) + проектные требования:

- **Auth-матрица**: «аноним / pending / viewer / admin» × «health /
  register / встроенная ручка / users-ручка / UI-страница» даёт
  ожидаемые 401/403/200.
- **Цикл регистрации**: «регистрация → отказ в логине (неактивен) →
  одобрение админом → успешный логин»; bootstrap админа на пустой БД;
  лимит pending-регистраций срабатывает; cookie login/logout.
- **Цикл уведомления**: «регистрация → команда `notify` в outbox →
  исполнение → done»; сбой `notify` не ломает регистрацию.
- **Пауза без потерь**: пауза (вкл. через `/ui/pipelines`) → события
  копятся в очереди → возобновление → доставка без потерь и дублей.
- **Requeue с attempt=0**: DLQ-запись возвращается в очередь и
  обрабатывается заново с `attempt=0`.
- **Контракты портов**: `RuntimeConfigPort` и `CommandOutboxPort` проходят
  контрактные наборы на InMemory + SQLAlchemy (атомарность взятия
  команды; приоритет override; failed-команда видна в аудите).
- **Аудит**: после каждой админ-операции в аналитике присутствует
  `admin_op`.
- **Bootstrap fail-fast** (FR-0): отсутствие `ANGARION_API__SECRET` /
  admin-env при `auth="users"`, а также невалидный `processor_config`
  (T021) → падение при `build_app`, до приёма событий.
- **Качество (проектные пороги)**: TDD; `ruff`/`ruff format`/`mypy
  --strict` — 0 ошибок; `pytest` зелёный; coverage ≥ 90% на `src/`.
- **Офлайн UI**: дашборд работает без сети/CDN (ассеты из пакета).
- **Документация (§17.9, deliverable этапа)**: deploy-гайд (systemd
  `Restart=always`, бэкапы, reverse proxy + TLS), гайд автора плагина с
  walkthrough по `angarion.testing`, справочник публичного API
  пополнен — без них релиз этапа не считается завершённым.

## 5. Key Entities

- **`AngarionDeps`** — контейнер портов из composition root (queue,
  analytics, registry, state, cursors, runtime-config, outbox + конфиг),
  кладётся в `app.state`.
- **`UserRow`** — пользователь (id, login, password_hash, role,
  is_active, registered_at, approved_at, approved_by).
- **`AppSettingRow`** — override динамической настройки (key, value JSON,
  updated_at, updated_by); за ним — DTO `DynamicSettings`.
- **`OutboxCommandRow`** — команда api→pipeline (id, kind, payload JSON,
  status pending/done/failed, created_at, executed_at, result/error).
- **`Page`** — дескриптор пользовательской UI-страницы (title, path,
  router) для `register_page` / `create_app(pages=...)`.
- **Событие `admin_op`** (аналитика) — аудит админ-операций и изменений
  динамики.
- **`config_model`** (T021) — хук контракта `ProcessorPort`, возвращающий
  Pydantic-модель для валидации `processor_config` на старте.

## 6. Assumptions & Constraints

- Стек web фиксирован ТЗ: FastAPI + fastapi-users (+ `-db-sqlalchemy`),
  Jinja2 + htmx + Pico.css. **Без Node/сборки**, ассеты в пакете.
- Хранилище — существующий SQLAlchemy 2.0 async + SQLite (WAL допускает
  конкурентных читателей: api-процесс читает те же `app.db`/`queue.db`).
- Telethon-клиенты живут **только** в pipeline-процессе; всё, что требует
  клиентов из api-процесса, идёт через командный outbox.
- Тестирование — TDD, ASGI через `httpx.AsyncClient(ASGITransport)` на
  **InMemory-портах** (без сети, БД, Telegram).
- По умолчанию bind `127.0.0.1`; выставление наружу (reverse proxy + TLS)
  — ответственность пользователя, но auth рассчитан на общую сеть.
- Перезапуск: подъём процесса — обязанность супервизора (systemd
  `Restart=always`); приложение делает только graceful shutdown.
- Python ≥ 3.12; coverage ≥ 90%; `mypy --strict`; `migrations/` вне
  линтеров/mypy/coverage.

## 7. Out of Scope

- Горизонтальное масштабирование, распределённый запуск (несколько
  pipeline-процессов на один аккаунт) — §3 ТЗ.
- Редактирование топологии пайплайнов / конструктор через UI — топология
  остаётся статической конфигурацией (§12.6, §12.8).
- Роли тоньше `admin`/`viewer` (RBAC, права на конкретный пайплайн) — v1
  ограничен двумя ролями.
- OAuth/SSO/внешние провайдеры идентичности — только локальный user store
  fastapi-users.
- Графические JS-библиотеки для визуализации — SVG строится на сервере.
- Медиа и второй мессенджер — это M7 (§12.10), не M5.
- Write-операции пользователя над доменом сверх админ-операций §12.8 —
  вне v1.

## Analyze (заполняется Claude)

Прогон spec + plan на противоречия/упущения/технические невозможности.

- 🟡 **Два писателя в `app.db`** (раздельный режим): api-процесс пишет
  users/settings/audit, pipeline — analytics/registry/outbox-статусы;
  SQLite = один писатель. Развязка: `PRAGMA busy_timeout` (поверх WAL) +
  ретрай записи на `database is locked`; записи api редкие. ADR при
  реализации T024 (plan §3.1). Не блокирует старт T022.
- 🟢 **`restart` во встроенном режиме** гасит pipeline вместе с api — by
  design; фиксируем в deploy-гайде, UI предупреждает (plan §3.2).
- 🟢 **Порядок Alembic-ревизий**: T023 (`UserRow`) и T024
  (`AppSettingRow`/`OutboxCommandRow`) — линейно поверх M2-схемы, каждая
  группа = своя ревизия; `auto_migrate=false` сохраняется (plan §3.4).
- 🟢 **Bootstrap fail-fast рассыпан по группам**: FR-0 объединяет
  концептуально, но `config_model` (T021) реализуется в T022, а
  api-secret/admin — в T023. Это ок: разные surface'ы конфига, общий
  принцип fail-fast. Зафиксировано в plan §4.
- 🟢 **Webhook-роутеры адаптеров** (ADR «AdapterPlugin без webhook_router
  до M5»): монтируются в T022 (API core) — закрывают долг M3. Проверить
  контракт `Listener.webhook_router` при реализации.
- 🟢 **Покрытие ≥ 90% на web-слое**: ASGI-тесты на InMemory-портах дают
  высокое покрытие без сети; SVG-рендер (T025) и шаблоны — через проверку
  маркеров в HTML. Риск недопокрытия ниже, чем у сетевого кода M3.

Чистый проход: 🔴 Critical отсутствуют — реализацию T022 можно начинать.
