## 1. Overview

T019 — **user-facing примеры** к процессорам M4 (T007), завершающие этап
по правилу «примеры как часть крупной фичи». Два сценария «как этим
пользоваться»:

1. **`examples/llm/`** — конвейер с встроенным процессором `llm`:
   входящие сообщения суммаризируются/переписываются локальной
   OpenAI-совместимой моделью (Ollama) и уходят в целевую группу. Только
   конфигурация + скрипт запуска (как `examples/forward`), без
   собственного кода.
2. **`examples/digest/`** — **пример stateful-процессора «дайджест»**
   (§16 M4, §10.3): пользовательский процессор накапливает входящие
   сообщения и периодически сбрасывает единым дайджестом в целевую
   группу. Демонстрирует работу с `svc.state` и идемпотентность под
   at-least-once.

Дайджест — **пример** (код в `examples/`, демонстрация контракта), а не
встроенный процессор `src/` (решение Q5 T007; §16 называет его «примером
stateful-процессора»).

## 2. User Stories

- Как **оператор**, я хочу готовый пример `examples/llm`, чтобы за
  минуты поднять суммаризацию сообщений локальной моделью и понять, как
  конфигурируется `llm`-процессор.
- Как **разработчик на базе angarion**, я хочу пример stateful-процессора
  «дайджест», чтобы понять, как писать **свой** процессор с состоянием
  (`svc.state`), накоплением и периодическим сбросом, и как делать его
  идемпотентным под at-least-once.
- Как **оператор дайджеста**, я хочу настраивать сброс по числу
  накопленных сообщений и/или по «возрасту» самого старого, чтобы
  получать сводку не слишком редко и не слишком дробно.

## 3. Functional Requirements

**`examples/llm/`**
- ДОЛЖНА: рабочий `app.toml` с пайплайном `processor = "llm"`
  (`base_url` на Ollama, `model`, `system_prompt`, `user_prompt`),
  источник/цель — тестовые группы; секреты/рантайм — git-ignored.
- ДОЛЖНА: `run.sh` «всё в одном» (idempotent migrate/login/run) и README
  с настройкой, запуском Ollama (`qwen2.5:3b`) и troubleshooting'ом —
  по образцу `examples/forward`.

**`examples/digest/` — процессор «дайджест»**
- ДОЛЖНА: пользовательский async-процессор, регистрируемый штатным
  механизмом (entry point `angarion.processors` примера / inline-`@processor`).
- ДОЛЖНА: на каждом приходящем событии добавлять его в накопитель в
  `svc.state` (JSON-сериализованная Pydantic-модель состояния).
- ДОЛЖНА: быть идемпотентной под at-least-once — повторная обработка того
  же события (по `dedup_key`) не задваивает запись (§10.3).
- ДОЛЖНА: сбрасывать накопленное единым `OutboundMessage` на каждую
  `ctx.targets` при срабатывании условия сброса; после сброса — очищать
  накопитель.
- ДОЛЖНА: условие сброса конфигурируемо — по числу `N` и/или по
  «возрасту» старейшего элемента `max_age`; проверка **на приходящем
  событии** (без фонового шедулера, §6.3).
- ДОЛЖНА: пример включать `app.toml` + `run.sh` + README.

**Тестируемость дайджеста**
- ДОЛЖНА: логика дайджеста покрыта unit-тестом, в т.ч. идемпотентность
  относительно повторной доставки события (at-least-once).

**Сверка существующих примеров**
- ДОЛЖНА: пройтись по `examples/forward` на актуальность публичного
  API/конфига (правило «при изменении API — обновить примеры»).

## 4. Success Criteria

- `examples/llm` воспроизводим по README: на поднятой Ollama сообщение
  проходит суммаризацию и доставляется в цель (ручной прогон).
- `examples/digest` воспроизводим по README: накопление → сброс
  дайджеста в цель работает end-to-end (ручной прогон).
- Unit-тест дайджеста зелёный, включая кейс «повторная доставка того же
  события не задваивает накопитель»; 4 проверки (ruff/format/mypy --strict/
  pytest) зелёные, coverage в пределах политики проекта.
- Секреты и рантайм примеров в репозиторий не попадают.

## 5. Key Entities

- **Состояние дайджеста** — Pydantic-модель в `svc.state` (накопленные
  элементы + метки времени + учтённые `dedup_key` для идемпотентности).
- **Элемент дайджеста** — что накапливаем по событию (напр. `sender_name`,
  `text`, `event_at`).
- **Конфиг дайджеста** (`processor_config`) — порог `N`, `max_age`,
  опц. шаблон строки элемента / заголовок сводки.

## 6. Assumptions & Constraints

- Worker конкурентен = 1, событийно-управляем (§6.3): сброс по `max_age`
  проверяется только при приходе события; при затишье дайджест ждёт.
- Состояние — через `svc.state` (namespace = пайплайн), значения —
  JSON-строки (§10.3).
- Локальная модель для `examples/llm` — Ollama в docker, `qwen2.5:3b`
  (N5 T007).
- Секреты/рантайм примеров — git-ignored, в файлах только плейсхолдеры.

## 7. Out of Scope

- Дайджест как встроенный процессор `src/` (остаётся примером; Q5 T007).
- Фоновый шедулер сброса по «настенному» времени без события (§6.3).
- Расширение `ProcessorPort` хуком `config_model` (это T021).

## Clarify (заполняется Claude)

### Open questions

- **Q1. Что эмитит дайджест при сбросе?** Варианты: (a) детерминированная
  склейка накопленных строк (заголовок + строки по шаблону); (b) прогон
  накопленного через `llm` (LLM-саммари батча) — эффектнее как «M4 LLM
  пример», но связывает дайджест с LLM-вызовом; (c) оба, переключаемо.
- **Q2. Идемпотентность — окно дедупа.** Хранить учтённые `dedup_key`
  только текущего накопителя (после сброса забываются) — тогда повторная
  доставка события **после** сброса может попасть в новый дайджест. Либо
  держать «хвост» недавно сброшенных ключей. Какой компромисс?
- **Q3. Где живёт код примера-дайджеста и как тестируется?** Чтобы быть
  покрытым unit-тестом, процессор должен быть импортируемым модулем
  (напр. `examples/digest/processor.py`), а тест — в `tests/` или рядом.
  Покрывается ли `examples/` политикой coverage `--cov=src` (нет — он вне
  `src/`)? Как организуем тест примера?
- **Q4. Один пример или два каталога?** `examples/llm` и
  `examples/digest` раздельно, или единый `examples/digest` с
  LLM-саммари (если Q1=b), а `examples/llm` — отдельный минимальный?
- **Q5. Сценарий `examples/llm`** — суммаризация (как acceptance T007),
  перевод, или переписывание? Влияет только на промпты в README.
- **Q6. Фазы и PR** — дробление T019 на фазы и число PR.

### Resolved (с ответами)

- **Q1+Q4 → один пример `examples/digest` с LLM-саммари.** Отдельного
  `examples/llm` нет: дайджест накапливает события и при сбросе прогоняет
  батч через LLM (сводка) → `ctx.targets`. Оба процессора-значения M4
  (stateful + LLM) показаны в одном сценарии. Минимальный `processor =
  "llm"`-пайплайн показываем сниппетом в README примера (чтобы встроенный
  `llm` тоже имел copy-paste-конфиг, см. A1).
- **Q2 → накопитель + ограниченный «хвост» сброшенных ключей.** В
  состоянии храним `dedup_key` текущего батча И ограниченный хвост недавно
  сброшенных (отсекает повтор после сброса). Размер хвоста — фикс. дефолт
  (см. A3).
- **Q3 → `examples/digest/processor.py` импортируемый + тест в `tests/`.**
  Unit-тест в `tests/unit/examples/` подключает каталог примера (conftest/
  importlib). Вне `--cov=src`, но гоняется в CI.
- **Q5 → сценарий: суммаризация** (как acceptance T007); промпт сводки в
  README.
- **Q6 → одна фаза, один PR** (объём примера невелик): процессор +
  конфиг/`run.sh`/README + тест + сверка `examples/forward`. Update
  (CHANGELOG/BOARD) — там же.

## Analyze (заполняется Claude)

### 🟡 Warning

- **A1. Встроенный `llm` без отдельного config-only примера.** Решение
  Q1 (один пример с LLM-саммари через кастомный код дайджеста) не
  показывает путь `processor = "llm"` напрямую. → Митигируем сниппетом
  «минимальный llm-пайплайн» в README `examples/digest` (та же Ollama/
  `base_url`/`model`). Отдельный каталог не заводим (решение Q1).
- **A2. Как дайджест вызывает LLM.** Переиспользуем `HttpxLlmClient` +
  `ChatMessage` из `angarion.application.llm` (DRY + инъектируемая
  граница → тест без сети). Это **не** часть публичной поверхности §16.3,
  поэтому при рефакторинге внутренностей пример надо будет поправить
  (правило «при изменении API — обновить примеры» это и так требует).
  Альтернатива (свой httpx в примере) — больше дублирования, отвергаем.
- **A3. Идемпотентность под at-least-once (§10.3).** Состояние:
  Pydantic-модель `{items: [...], seen: [dedup_key батча], recent:
  [хвост сброшенных]}`. На событии: если `dedup_key ∈ seen ∪ recent` —
  пропуск (идемпотентность). Хвост `recent` ограничен (дефолт, напр.
  100 ключей) — иначе состояние растёт бесконечно. Тест: повторная
  доставка в батче и после сброса не задваивает.
- **A4. Сброс под worker=1 (§6.3).** `max_age` проверяется только на
  приходящем событии; при затишье дайджест ждёт следующего события —
  осознанно (как honored FloodWait M3). Документируем в README.
- **A5. Тестируемость LLM-сброса без сети.** Дайджест-процессор принимает
  границу `LlmHttpClientPort` (дефолт — реальная `HttpxLlmClient`); тест
  подставляет fake/`MockTransport` (как llm-тесты T007). Сброс по `N`
  детерминирован; `max_age` тестируется инъекцией «часов»/`event_at`.
