# Spec: Лёгкий поллинг недавнего окна — backstop правок/удалений (T032)

**Статус:** Analyzed
**Дата создания:** 2026-06-19
**Связанные документы:** `BACKLOG.md` (T032), `specs/T009-m6-integration/spec.md`
(ненадёжность live-апдейтов), `src/angarion/adapters/telegram/catchup.py` и
`src/angarion/adapters/matrix/listener.py` (§9.3), `DECISIONS.md` (ретро M6)

## 1. Overview

Live-апдейты Telegram (и отчасти Matrix) ненадёжны (всплыло в M6/T009): часть
правок и удалений не доезжает событиями. Сейчас единственный backstop —
периодический catch-up (`[catchup] interval`), который каждый интервал
пере-сканирует до `max_messages_per_source` (дефолт 2000) истории на источник.
На больших/активных группах это дорого и упирается в лимиты, поэтому интервал
держат редким — и правка «провисает» до следующего глубокого прохода.

Фича вводит **отдельный лёгкий режим**: частую (≈30 с) сверку только **узкого
недавнего окна** (последние N сообщений, но не старше M минут) — дёшево ловит
правки и удаления свежих сообщений, в дополнение к редкому глубокому catch-up,
который остаётся страховкой на длинный хвост. Режим — **opt-in на пайплайн**;
по умолчанию выключен (дополнительный трафик — осознанный выбор). Работает на
**обеих** платформах (Telegram, Matrix), переиспользуя их существующую логику
детекции, но по узкому окну.

## 2. Сценарии использования

- Как оператор зеркала активной группы, я хочу, чтобы правка только что
  пересланного сообщения подхватывалась за десятки секунд, не гоняя
  пере-скан тысяч сообщений, чтобы зеркало не отставало и не жгло лимиты.
- Как оператор, я хочу ловить быстрое удаление свежего сообщения
  («опечатался, удалил»), даже если live-событие удаления не пришло, без
  ежеминутного глубокого catch-up.
- Как оператор большой группы, я хочу держать глубокий catch-up редким
  (раз в часы) ради лимитов, не теряя оперативность по свежим правкам, и
  включать лёгкий поллинг только на тех пайплайнах, где он нужен.

## 3. Functional Requirements

- ДОЛЖНА: периодически (интервал `[catchup] recent_interval`, дефолт ≈30 с)
  сверять **узкое недавнее окно** источника и эмитить правки/удаления через
  существующую per-adapter логику catch-up (Q9), но по окну, а не по всей
  истории.
- ДОЛЖНА: ограничивать окно **одновременно** числом (последние N,
  `recent_window_messages`) и возрастом (не старше M минут,
  `recent_window_minutes`) — окно = min(N, M) (Q1).
- ДОЛЖНА: НЕ эмитить ложные удаления для сообщений **ниже окна** (узкая
  выборка не покрывает старое — пропуск лучше ложного удаления, §9.3
  truncation-guard уже это обеспечивает для Telegram).
- ДОЛЖНА: эмитить события в тот же `IngestService` (`origin='catchup'`),
  чтобы дедуп (§7.4) гасил пересечения с live и глубоким catch-up.
- ДОЛЖНА: включаться **per-pipeline** (флаг `[pipelines.*].recent_poll`,
  дефолт `false`, по образцу `forward_media`/T033). Глобальные параметры
  окна/частоты — в `[catchup]` (Q5/Q6).
- ДОЛЖНА: поллить источник, входящий **хотя бы в один** пайплайн с
  `recent_poll = true` (исполнение — на уровне listener'а/источника,
  конфиг — на уровне пайплайна; см. Analyze 🟡-1).
- ДОЛЖНА: работать на Telegram и Matrix, переиспользуя их catch-up:
  Telegram — registry-diff по хэшам + missing→deletion; Matrix — события
  `m.replace`/redaction в окне истории (Q7/Q9).
- ДОЛЖНА: не двигать курсоры так, чтобы ломать глубокий catch-up: Telegram
  делит `last_seen`-курсор (безопасно — NEW глубокого прохода решается по
  реестру), Matrix `next_batch` (sync-позиция live) **не трогает** (Q3).
- ДОЛЖНА: обходить источники последовательно/с jitter, не бить history-API
  залпом (Q4).
- НЕ ДОЛЖНА: заменять глубокий catch-up (остаётся backstop на длинный хвост).
- НЕ ДОЛЖНА: шуметь `catchup_truncated` на каждый проход (узкое окно
  «усечено» by design — для лёгкого режима это событие подавляется,
  Analyze 🟡-2).

## 4. Success Criteria

- Правка сообщения в недавнем окне ловится без полного пере-скана: лёгкий
  проход фетчит ≤ `recent_window_messages` (а не `max_messages_per_source`).
- Удаление сообщения в недавнем окне эмитит ровно один `MESSAGE_DELETED`
  (Telegram — chat-уровень §9.4; Matrix — redaction в окне), без ложных
  удалений ниже окна.
- Стоимость одного прохода предсказуема: один history-запрос с малым
  лимитом на источник, обход с jitter.
- Окно (N, M) и частота конфигурируемы (`[catchup]`); включение —
  per-pipeline (`recent_poll`), по умолчанию выключено.
- Покрыто тестами на fake-клиентах обеих платформ: правка/удаление в окне
  ловятся; ниже окна — нет; дедуп с глубоким catch-up не даёт двойной
  эмиссии; курсоры не повреждаются.

## 5. Key Entities

- **Недавнее окно** — узкая выборка верхних сообщений источника:
  min(N последних, не старше M минут).
- **Курсор источника** (`SourceCursor`, §9.2): Telegram —
  `last_seen_external_id` (делится с глубоким catch-up), Matrix —
  `next_batch` (лёгкий поллинг его не трогает). Новых таблиц фича не вводит.
- **Запись реестра** (`RegistryRecord`) — источник истины сверки для
  Telegram (хэши + набор известных id).
- **Лёгкий поллер** — фоновый таймер per source (аналог `_periodic_catchup`),
  малое окно, частый интервал; живёт в listener'е каждого адаптера.
- **`[pipelines.*].recent_poll`** — boolean opt-in пайплайна.

## 6. Assumptions & Constraints

- Платформы v1 — **Telegram и Matrix** (Q7). Оба listener'а уже имеют
  `catchup(source_key)` + `fetch_history(limit=...)` — лёгкий поллинг
  параметризует их окном, детекцию не дублирует (Q9).
- history-API лимитируются; частота × число источников выбирается с запасом,
  обход с jitter; FloodWait/троттлинг — существующая забота §12.8.
- Telegram-удаления — только chat-уровень (`thread_id=None`), как live и
  catch-up (§9.4). Matrix-удаления — redaction-события в окне.
- Дедуп (§7.4) гасит повторную эмиссию NEW; EDITED самогасится сверкой по
  реестру (Telegram) / отсутствием нового `m.replace` (Matrix).
- Реестр и курсоры персистентны (M2).

## 7. Out of Scope

- Замена/переписывание глубокого catch-up (§9.3) — остаётся как есть.
- Починка надёжности live-апдейтов (это backstop, не лечение live).
- Детекция удалений ниже окна и в топиках (как и сейчас не покрывается).
- Унифицированный кросс-платформенный registry-diff (Q9 — переиспользуем
  per-adapter детекцию; единый алгоритм отвергнут).
- Новые таблицы/порты персистентности.

### Resolved (с ответами)

- **Q1 (окно).** Окно = **min(N последних, не старше M минут)** — самый
  предсказуемый по стоимости вариант.
- **Q2 (частота/дефолт).** Режим **выключен по умолчанию**; интервал
  лёгкого прохода ≈ **30 с**; дефолтный размер окна ≈ **30 сообщений**.
  Дефолт M (минут) — предложение **10 мин** (Analyze 🟢-3 — подтвердить).
- **Q3 (курсор).** Telegram — **общий** `last_seen`-курсор с глубоким
  catch-up (безопасно: NEW глубокого решается по реестру, свежие NEW лёгкий
  проход эмитит сам). Matrix — `next_batch` (sync-позиция) **не трогаем**:
  его catch-up фетчит окно независимо.
- **Q4 (залп).** Обход источников последовательный/с jitter (как
  `_periodic_catchup`), без залпа в history-API.
- **Q5 (конфиг).** Расширяем **`[catchup]`** (`recent_interval`,
  `recent_window_messages`, `recent_window_minutes`) — та же подсистема.
- **Q6 (область).** Включение **per-pipeline** (флаг
  `[pipelines.*].recent_poll`, дефолт `false`, по образцу `forward_media`).
- **Q7 (платформа).** **Telegram + Matrix** сразу.
- **Q8 (удаления).** Telegram — в пределах окна и только chat-уровень;
  Matrix — redaction-события в окне. «Ниже окна» и топики — на глубоком
  catch-up.
- **Q9 (детекция).** **Переиспользуем per-adapter catch-up** по узкому окну:
  TG — registry-diff, Matrix — `m.replace`/redaction. Единый registry-diff
  отвергнут (Matrix плохо ложится, лишний scope).

## Analyze (заполняется Claude)

- 🟡 **A-1 (per-pipeline конфиг → per-source исполнение).** `recent_poll` —
  флаг пайплайна, но поллинг крутится в listener'е на уровне источника.
  Источник может входить в несколько пайплайнов. **Резолв:** источник
  поллится, если он — источник **хотя бы одного** пайплайна с
  `recent_poll = true`; bootstrap собирает объединение таких источников и
  отдаёт listener'у (как уже резолвит `ResolvedSource`). Зафиксировать в
  plan: где именно вычисляется множество (composition root, рядом с
  резолвом источников).
- 🟡 **A-2 (шум аналитики).** Узкое окно почти всегда «truncated» →
  `run_catchup` (Telegram) эмитнул бы `catchup_truncated` каждый проход.
  **Резолв:** лёгкий режим не пишет `catchup_truncated` (флаг режима в
  `run_catchup` или отдельная тонкая обёртка, подавляющая это событие).
  Аналогично — не плодить `catchup`-аналитику на каждый 30-с проход.
- 🟢 **A-3 (дефолт M).** Дефолт `recent_window_minutes` предложен 10 мин —
  подтвердить при ревью; не блокирует.
- 🟢 **A-4 (Telegram thread-источники).** Для `thread_id != None` удаления
  не детектятся (как и сейчас, §9.4) — правки по окну работают, удаления —
  только глубокий проход. К сведению, не дефект.
- 🟢 **A-5 (Matrix окно по min_id).** `fetch_history` Matrix пагинирует от
  свежих с `limit`, без `min_id` — окно задаётся `limit` (N) + отсечкой по
  возрасту (M) в обёртке. Telegram `fetch_history` принимает `min_id` и
  возраст — окно строится симметрично. Унификация окна — на уровне обёртки
  лёгкого прохода, не самих `fetch_history`.
- 🟢 **A-6 (фазирование реализации).** Implement двумя фазами: (1) Telegram
  (registry-diff, общий курсор) + конфиг + per-pipeline резолв; (2) Matrix
  (окно над его catch-up). Каждая фаза — отдельный коммит/сессия.
