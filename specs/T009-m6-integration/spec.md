**Статус:** Done

**Связанные документы:** `CONCEPT.md` §13.2, §16 (M6); `DECISIONS.md`

## 1. Overview

M6 закрывает уровень интеграционных тестов §13.2: прогон **всего
пайплайна** на **реальном тестовом Telegram-аккаунте** и нескольких
тестовых группах. Тесты помечены маркером `integration`, по умолчанию
skip (в обязательный CI-набор не входят, реквизиты — только из
`.secrets`/env). Покрываются сценарии live new/edited/deleted сквозь
пайплайн, multicast, рестарт с непустой очередью, catch-up и дедуп при
повторном catch-up; тесты прибирают за собой.

Вторая, сознательно включённая в M6 часть (решение Владимира 2026-06-16,
см. Clarify) — **петлевой guard**: механизм, позволяющий безопасно
направлять пайплайн в группу, которая одновременно является источником
(`source == target`), не зацикливаясь на собственных доставках. Без него
сценарий «источник = одна из целей» (вариант 2 топологии) невозможен.

## 2. Сценарии использования

Явных «пользователей» нет — это инфраструктура тестирования и
поведенческая гарантия библиотеки. Сценарии:

- Как мейнтейнер, я хочу прогнать `pytest -m integration` на реальном
  аккаунте, чтобы убедиться, что весь пайплайн (listener + catch-up +
  очередь + worker + sender) работает против настоящего Telegram, а не
  только против fake-клиента.
- Как пользователь библиотеки, я хочу настроить пайплайн, где целевая
  группа совпадает с источником (агрегатор, который дописывает в тот же
  чат), и не получить бесконечную петлю собственных доставок.

## 3. Functional Requirements

### 3.1. Петлевой guard (core/adapter, в CI)

- ДОЛЖНА: после успешной доставки в target, совпадающий с прослушиваемым
  источником `(account_id, chat_id, thread_id)`, система помечает
  `dedup_key` будущего входящего `MESSAGE_NEW` произведённого сообщения
  (`make_dedup_key(MESSAGE_NEW, source_key, receipt.external_id)`), так
  что при возврате этого сообщения (live или catch-up) `IngestService`
  отбрасывает его как `duplicate`.
- ДОЛЖНА: использовать существующий `DedupStorePort` (персистентный,
  переживает рестарт, имеет `prune`) — без новых портов и таблиц.
- ДОЛЖНА: быть messenger-agnostic — реализована как декоратор
  `MessageSinkPort` на application-границе, не внутри Telegram-адаптера.
- ДОЛЖНА: подключаться в `build_app` только когда среди целей пайплайнов
  есть совпадение с источником (иначе декоратор — no-op, без накладных).
- НЕ ДОЛЖНА: менять контракт `MessageSinkPort`, ядро fan-out/worker,
  семантику dedup_key (формат ключей — публичный контract §7.2).
- МОЖЕТ: дополнительно помечать `dedup_key` удаления
  (`...:del`) произведённого сообщения, чтобы self-cleaning удалений в
  совмещённой группе не эмитил `MESSAGE_DELETED` (решается на Implement).

### 3.2. Интеграционный контур §13.2 (маркер `integration`, default-skip)

- ДОЛЖНА: собирать **настоящий** пайплайн через `build_app` на реальных
  backend'ах (sqlite storage, persistqueue) с реальным Telethon-клиентом
  (сессия из `.secrets`/`sessions/integration`).
- ДОЛЖНА: драйвить сообщения в источник **через live-клиент самого
  пайплайна** (взять подключённый клиент из `ClientPool` собранного app):
  один коннект → апдейты гарантированно доходят до listener'а (две
  параллельные Telethon-сессии на одном auth-key чреваты пропуском
  апдейтов — отвергнуто).
- ДОЛЖНА: покрывать сценарии:
  1. **Live new/edited/deleted** сквозь пайплайн: источник A → цель B;
     отправить → проверить доставку `MESSAGE_NEW`; отредактировать →
     `MESSAGE_EDITED` (с `previous_text`); удалить → `MESSAGE_DELETED`.
  2. **Multicast** (вариант 1, 3 группы): источник A → цели {B, C};
     одно сообщение доходит в обе цели.
  3. **Catch-up**: остановить listener → внести правки/удаления/новое в
     источнике → запустить → проверить эмиссию событий за простой.
  4. **Дедуп при повторном catch-up**: второй прогон catch-up не
     порождает повторных доставок.
  5. **Рестарт с непустой очередью**: persistqueue + пауза sender
     (динамический лимит / недоступная цель), накопить элементы в
     очереди, рестартовать `build_app` на том же файле, проверить
     доставку без потерь и дублей.
  6. **Петлевой guard / вариант 2** (2 группы, `source == target`):
     источник A → цели {A, B}; доставка в A не зацикливается (guard),
     при этом доходит в B.
- ДОЛЖНА: **самоочистка** — все отправленные тестом и пайплайном
  сообщения удаляются в teardown (best-effort, не маскируя падение
  ассертов).
- ДОЛЖНА: темп с запасом под лимиты Telegram (троттлинг sender'а +
  паузы ожидания доставки с polling истории цели).
- НЕ ДОЛЖНА: попадать в обязательный CI-набор; при отсутствии
  `.secrets`/сессии — skip с понятным сообщением (как T014).

## 4. Success Criteria

- `pytest -m integration` зелёный на реальном аккаунте (набор §13.2).
- `pytest` (обязательный набор, без `integration`) остаётся зелёным;
  петлевой guard покрыт unit/contract + fake-client e2e (source==target
  не зацикливается), coverage ≥ 90% держится.
- Четыре pre-push проверки (ruff check / format / mypy --strict /
  pytest) — 0 ошибок.
- Прогон контура не оставляет сообщений в тестовых группах (самоочистка).

## 5. Key Entities

- **`LoopGuardSink`** — декоратор `MessageSinkPort`: `inner` (реальный
  sender), `dedup: DedupStorePort`, множество source-ключей; помечает
  dedup произведённого сообщения, когда цель = источник.
- **Топология групп** — `TG_TEST_GROUP_A` (источник), `B`, `C` (цели);
  вариант 1 (3 группы, чистый multicast), вариант 2 (A — источник и
  цель, guard).
- **Интеграционные фикстуры** (`tests/integration/conftest.py`) —
  `tg_env` (+ группа C), сборка реального app, доступ к live-клиенту
  пула, хелперы ожидания/очистки.

## 6. Assumptions & Constraints

- Один реальный тестовый аккаунт (§13.2), сессия — git-ignored файл
  `sessions/integration` (создаётся `scripts/tg_login.py`).
- Три тестовые группы; рекомендованы супергруппы (id `-100…`).
- Telethon `events.NewMessage()` подписан без фильтра incoming/outgoing
  → listener видит и собственные исходящие сообщения аккаунта (на этом
  стоит self-driving источника).
- Реальный Telegram: тайминги недетерминированы → ожидание доставки
  через polling истории цели с таймаутом и щадящим темпом.
- persistqueue нужен для сценария рестарта (memory-очередь не переживает
  перезапуск).

## 7. Out of Scope

- Второй мессенджер / медиа (M7).
- Sender-based loop guard (фильтр «свой `sender_id`») — отвергнут:
  конфликтует с self-driving (драйвер = тот же аккаунт). См. Clarify.
- Reaper зависших `taken` (T027), ретеншн acked queue.db (T016) —
  отдельные задачи.
- Любые изменения публичного формата ключей §7.2/§7.3.
- Пример в `examples/` — по правилу проекта M6 (инфраструктура/
  тестирование) примера не требует.

## Clarify (резолв 2026-06-16, диалог с Владимиром)

### Resolved

- **Топология групп.** Реализуем вариант 1 (3 группы: источник + 2
  цели, чистый multicast без петель) **и** вариант 2 (2 группы,
  `source == target`, через петлевой guard). → §3.2, §5.
- **Драйвер сообщений.** Через live-клиент самого пайплайна (один
  коннект); параллельная вторая Telethon-сессия и отдельный второй
  аккаунт отвергнуты. → §3.2.
- **Рестарт с непустой очередью.** persistqueue + пауза sender (накопить
  элементы, рестартовать, проверить дослыку). → §3.2 (5).
- **Петлевой guard в scope M6.** Владимир сознательно включил guard в
  M6, с полным знанием, что (а) sender-based фильтр несовместим с
  self-driving, (б) корректный id-based guard тянет персистентность и
  взаимодействие с catch-up, (в) Claude рекомендовал вынести guard в
  отдельную задачу T030 — решение оставить в M6 принято осознанно.
  Дизайн упрощён: guard переиспользует персистентный `DedupStorePort`
  (pre-mark dedup_key), без новых портов/таблиц. → §3.1.

## Analyze (Claude, 2026-06-16)

- 🟢 **Guard и MESSAGE_EDITED/DELETED собственных доставок.** Пайплайн
  порождает только новые сообщения в цели (`send_message`), свои
  доставки не правит → достаточно pre-mark `MESSAGE_NEW`. Удаление
  произведённых сообщений (self-cleaning в совмещённой группе) может
  эмитить `MESSAGE_DELETED`: на Implement решить, помечать ли и `:del`
  ключ. Note, не блокер.
- 🟢 **dedup.prune и guard-маркеры.** Маркеры живут в том же
  `DedupStorePort`, подчиняются общему `prune(older_than)` (§17.3) — рост
  ограничен штатной уборкой, отдельной политики не нужно.
- 🟡 **Доступ к live-клиенту пула из теста.** Драйв через клиент
  пайплайна требует достать подключённый клиент из `ClientPool`
  собранного `app`. Сейчас pool доступен внутри listener'а; нужен
  аккуратный seam (свойство app/deps, отдающее pool/клиентов), чтобы не
  лезть в приватные поля. Решить на Phase 2; seam — тестовый, публичный
  API не расширяем без необходимости.
- 🟡 **Тайминг рестарт-сценария.** Пауза sender через динамический лимит
  даёт «висящие» элементы в persistqueue, но требует, чтобы worker
  успел взять их из очереди и упереться в троттлинг/недоступную цель.
  Альтернатива — недоступная цель (несуществующий chat) даёт надёжный
  failed→reschedule, но это уже DLQ-путь, не «непустая очередь». На
  Phase 3 выбрать надёжный способ держать очередь непустой в момент
  рестарта (вероятно: огромная пауза sender + проверка `queue.depth`).
- 🟢 **Самоочистка не должна маскировать падения.** Teardown удаляет
  best-effort в `finally`, ассерты — в теле; падение ассерта видно,
  очистка всё равно отрабатывает.
- 🟢 **CI-изоляция.** `addopts … -m 'not integration'` уже исключает
  маркер; обязательный набор не затрагивается. Guard-тесты (fake-client)
  идут в обычный набор.

## Итог реализации (2026-06-16)

`pytest -m integration` зелёный на реальном аккаунте (**8 passed**):
new/edited/deleted сквозь пайплайн, multicast (3 группы), дедуп при
повторном catch-up, рестарт с непустой очередью, петлевой guard
`source==target`, + smoke-доступ. Acceptance §16 M6 выполнен.

**Отклонение от Clarify-решения «драйв через live-клиент пайплайна».**
При прогоне выяснилось: приём **собственных** live-апдейтов одним
аккаунтом в тихую супергруппу ненадёжен (per-channel `pts` gap в
Telethon — артефакт self-send, не боевого пути; **входящие** от других
приходят штатно). Поэтому контур переведён на **catch-up-драйв**:
драйвер пишет/правит/удаляет отдельным `idle_client` пока app
остановлен, события поднимаются детерминированной history-реконсиляцией
(`iter_messages`) при старте; источник чистится перед сценарием
(`purge_recent`). Это надёжно и не зависит от update-state.

**Сопутствующие задачи, выявленные контуром:**
- **T030** — `get_me`+`catch_up` в `connect_client` (реконсиляция
  update-state). Первоначально расценён как «прод-баг», по итогам
  диагностики — улучшение робастности (основной прод-сценарий —
  зеркалирование входящих — работал и без него). ADR 2026-06-16.
- **T031** (BACKLOG) — graceful shutdown виснет, если `DeliveryWorker`
  залип в долгом throttle-ожидании (всплыло на frozen-sender варианте
  рестарт-теста; обошли — рестарт-сценарий не морозит sender).
