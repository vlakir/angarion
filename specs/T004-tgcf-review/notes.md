# T004 — Ревизия исходников tgcf перед M3

**Что это:** конспект ревизии исходников [tgcf](https://github.com/aahnik/tgcf)
(**v1.1.8**, лицензия **MIT**, © 2020 Aahnik Daw) по четырём темам §16 M3:
FloodWait/реконнекты, пагинация истории, резолв сущностей, session string.
Цель — снять полезные решения под MIT с атрибуцией и зафиксировать
«брать / не брать» перед реализацией Telegram-адаптера (T005, M3).

**Статус:** информационный документ к планированию M3. Решения в сжатом
виде — ADR «2026-06-13 — Ревизия tgcf (T004)» в `DECISIONS.md`.

**Контекст из ТЗ:** §15.18 (item 18) — интеграция tgcf как зависимости
**отклонена** (глобальное состояние, нет публичного API, нарушает изоляцию
ядра); принято заимствовать отдельные решения под MIT с атрибуцией.
§16 M3 — «перед реализацией ревизия исходников tgcf».

Исходники изучены по immutable-срезу: commit
[`f0d5859`](https://github.com/aahnik/tgcf/commit/f0d5859acfda4aa234d3c5316f14eb3b38e5f7ce)
(2023-12-06, ветка `main`, версия пакета v1.1.8). Зафиксирован явно, т.к.
`main` мутабельна — ссылки на файлы/строки ниже воспроизводимы только
относительно этого коммита. В репозиторий angarion код tgcf не копируется.

## Общая картина архитектуры tgcf

tgcf — standalone-приложение (Streamlit web UI + Telethon), не библиотека.
Два режима: **live** (`live.py`, подписка на события) и **past**
(`past.py`, прогон по истории). Состояние — глобальные модульные
переменные: `config.CONFIG`, `config.from_to` (карта роутинга),
`storage.stored` (карта пересланных сообщений для edit/delete-синка).
Конфиг — JSON-файл `tgcf.config.json` или MongoDB.

Именно это глобальное состояние и отсутствие публичного API — причина
отказа от tgcf как зависимости (§15.18). Гексагональное ядро angarion
(домен/порты/application, M1–M2) — прямая противоположность; tgcf полезен
как **референс приёмов работы с Telethon**, не как образец архитектуры.

## 1. FloodWait / реконнекты

### Как сделано в tgcf

- **Live (`live.py`)** — FloodWait **не обрабатывается вообще**. Вся
  работа делегирована Telethon: `client.run_until_disconnected()`
  (`live.py:165`) + дефолтные `auto_reconnect=True`, `connection_retries=5`,
  `flood_sleep_threshold=60`. Telethon сам спит на FloodWait ниже порога;
  выше — пробрасывает `FloodWaitError`, которую live-хендлеры не ловят →
  необработанное исключение в обработчике события (сообщение теряется,
  только лог).
- **Past (`past.py:81-83`)** — FloodWait ловится явно:
  ```python
  except FloodWaitError as fwe:
      logging.info(f"Sleeping for {fwe}")
      await asyncio.sleep(delay=fwe.seconds)
  ```
  **Но `except` обрамляет весь блок обработки сообщения в цикле
  `async for`** — после сна цикл переходит к **следующему** сообщению,
  а вызвавшее FloodWait сообщение **не ретраится → теряется**.
- **Троттлинг past** — фиксированный `time.sleep(CONFIG.past.delay)`
  (`past.py:78`), delay 0..100 c между сообщениями. Это **блокирующий**
  `time.sleep`, а не `asyncio.sleep` — морозит event loop.
- Реконнект — целиком на Telethon, своей логики нет.

### Решения для angarion

| Приём | Брать? | Почему |
|---|---|---|
| Базовый авто-реконнект Telethon (`auto_reconnect`, `connection_retries`, `retry_delay`) как фундамент | **Брать (идея)** | Правильный baseline; в M3 явно конфигурируем эти параметры клиента, не пишем реконнект сами |
| Опираться на `flood_sleep_threshold` для коротких FloodWait | **Брать (идея)** | Telethon сам спит на мелких флудах — оставить включённым, порог вынести в конфиг |
| Игнорировать FloodWait в live (как tgcf) | **Не брать** | Потеря событий выше порога; M3 требует устойчивый троттлинг. Ловить `FloodWaitError` и **ретраить то же** действие после сна |
| Пропуск сообщения после FloodWait в catch-up (баг past.py) | **Не брать** | Прямая потеря данных; catch-up обязан повторить то же сообщение (наш at-least-once §7.1) |
| `time.sleep()` между сообщениями | **Не брать** | Блокирует event loop — антипаттерн; только `asyncio.sleep`. Троттлинг — через токен-бакет/задержку в адаптере |

**Вывод:** у tgcf брать нечего на уровне кода — лишь подтверждение, что
baseline Telethon (авто-реконнект + flood-порог) достаточно как фундамент,
а прикладной слой M3 должен добавить **ретрай-после-сна без пропуска** и
**неблокирующий троттлинг**. Pattern из past.py — пример того, как
**не** надо (skip + `time.sleep`).

## 2. Пагинация истории (catch-up / past mode)

### Как сделано в tgcf (`past.py`)

- Один примитив: `client.iter_messages(src, reverse=True, offset_id=forward.offset)`.
  - `reverse=True` → хронологический порядок (старые первыми) — правильно
    для catch-up.
  - `offset_id` = id последнего обработанного сообщения → рестарт
    продолжает с места обрыва.
- Сама пагинация (`GetHistoryRequest` батчами) — внутри `iter_messages`,
  tgcf вручную не страничит.
- **Курсор-персист:** после каждого пересланного сообщения
  `forward.offset = last_id` и `write_config(CONFIG, persist=False)` —
  перезапись offset в конфиг **после каждого сообщения**. Крэш →
  продолжение с последнего записанного offset.
- `forward.end` — опциональная верхняя граница id.
- Пропуск `MessageService` (системные: вступления/пины/…) — `past.py:55`.

### Решения для angarion

| Приём | Брать? | Почему |
|---|---|---|
| `iter_messages(reverse=True, offset_id=cursor)` как примитив catch-up | **Брать (концепт)** | Ровно то, что нужно для §9; наш непрозрачный курсор (адаптер `cursors`, T002/T003) ложится на `offset_id` напрямую |
| Частая персистенция курсора | **Брать (концепт, наш механизм)** | У нас уже транзакционный `CursorPort` (M2) — лучше, чем перезапись JSON. Берём **семантику** offset_id, не механизм |
| Пропуск `MessageService` в catch-up | **Брать** | Системные сообщения не несут контента — отсеивать на входе адаптера |
| `forward.end` как верхняя граница | **Брать (опц.)** | Полезно для ограниченного backfill; в M3 — опциональный параметр |
| Перезапись всего JSON-конфига после каждого сообщения | **Не брать** | Чудовищный I/O + связка курсора с конфигом; у нас отдельный async `CursorPort` |

**Вывод:** концептуально tgcf делает ровно правильную вещь
(`iter_messages` + offset_id-курсор), и это **валидирует наш дизайн**
курсора из M1/M2. Механизм персиста (JSON-перезапись + `time.sleep`) — не
брать, у нас он уже лучше.

## 3. Резолв сущностей (entity resolution)

### Как сделано в tgcf (`config.py:164-208`)

- `get_id(client, peer) = await client.get_peer_id(peer)` — резолвит
  username / телефон / ссылку / id → знаковый int chat id.
- `load_from_to()` — **один раз на старте** конвертирует все
  источники/получатели из конфига (которые могут быть username/phone/link/int)
  в карту знаковых int chat id. Весь рантайм-роутинг, storage и edit/delete-синк
  ключуются строго по int id.
- В коде есть прямой комментарий-обоснование (`config.py:181-186`):
  > знаковые int chat id стабильны и существенны для storage; storage
  > существенен для edit/delete/reply-синка.

### Решения для angarion

| Приём | Брать? | Почему |
|---|---|---|
| Резолв всех human-friendly ссылок (username/link/phone) в стабильный числовой peer id **однократно**, ключевать роутинг/дедуп/реестр по нему | **Брать (концепт)** | Совпадает с нашим доменным ключеванием (`domain/keys`, `thread_id`); **валидирует дизайн M1**. Username/ссылки меняются — числовой id стабилен |
| Обоснование «числовой id — стабильная идентичность» | **Брать (как принцип)** | Уже так делаем; фиксируем как явный принцип Telegram-адаптера |
| Резолв только на старте из статического конфига | **Не брать как есть** | У нас пайплайны управляются из UI (M5) динамически — резолв должен быть **повторяемым** при смене конфига |
| Отсутствие обработки ошибок резолва (исключение всплывает) | **Не брать** | Адаптер M3 обязан обрабатывать неудачу резолва (приватный/удалённый чат, нет доступа) штатно, не падать |

**Важный gotcha (tgcf обходит молча):** Telethon для отправки
(`send_message`/`get_input_entity`) нуждается в сущности в кэше сессии.
tgcf резолвит на старте тем же клиентом с **тёплым** кэшем, поэтому
проблема не проявляется. При **холодном** кэше (свежая сессия) резолв
только по числовому id может падать `Could not find the input entity`.
**Адаптер M3 должен прогревать кэш** (резолв через username/`get_dialogs`)
или хранить `input_peer` — нельзя полагаться на «id просто сработает».

## 4. Session string

### Как сделано в tgcf

- `config.get_SESSION()` (`config.py:250-260`): при `user_type==1` и
  непустом `SESSION_STRING` → `StringSession(SESSION_STRING)`; для бота —
  файловая сессия по имени. Иначе `sys.exit()`.
- `SESSION_STRING` хранится в конфиге (**JSON-файл или Mongo**)
  **открытым текстом** в поле `LoginConfig.SESSION_STRING`.
- **Генерация session string — НЕ в tgcf.** Делегирована внешнему
  инструменту `tg-login` (отдельный репозиторий / replit). Web UI лишь
  даёт текстовое поле «вставьте session string». Разработчик прямо пишет,
  что логин по номеру телефона в web UI «не поддерживается из-за проблем».
- `clean_session_files()` (`utils.py:95-98`): на старте удаляет все
  `*.session` / `*.session-journal` в cwd — раз используется StringSession,
  файловые сессии-сироты чистятся во избежание путаницы/локов.

### Решения для angarion

| Приём | Брать? | Почему |
|---|---|---|
| `StringSession` как первоклассный вариант сессии | **Брать (концепт)** | Портативна, без файловых локов, удобна для мультиаккаунта (§ M3) и контейнеров |
| Хранить session string **открытым текстом** в конфиге | **Не брать** | Это полные учётные данные аккаунта (как `.session`, см. CLAUDE.md/§17.6). Хранить зашифрованно / `chmod 600` / вне логов (§17.7 — маскирование) |
| Делегировать генерацию внешнему replit/инструменту | **Не брать** | Генерация — в CLI angarion (`angarion login` или аналог). Прецедент уже есть: `scripts/tg_login.py` из T014 |
| `clean_session_files()` при StringSession | **Брать (мелочь)** | Избежать сирот-файлов; у нас `*.session` уже в `.gitignore` |

**Открытое решение для M3:** файловая сессия (`.session`, как в нашем
интеграционном контуре T014 — `sessions/integration.session`) **vs**
StringSession-в-БД на аккаунт. tgcf выбрал StringSession-в-конфиге. Для
мультиаккаунта M3 это надо решить на этапе спеки T005 (файлы проще и
лочатся; StringSession портативнее и ложится в БД). — фиксируется как
вопрос к спеке M3, не закрывается здесь.

## Чего НЕ заимствовать (антипаттерны, валидирующие наш дизайн)

Эти места tgcf — не «приёмы для заимствования», а подтверждение, **почему**
наша архитектура устроена иначе (полезно как обоснование в спеке M3):

- **Глобальное мутабельное состояние** (`config.from_to`, `storage.stored`,
  `CONFIG`) — корень отказа от tgcf-as-dependency (§15.18). Наши
  порты/DI — прямая замена.
- **`storage.stored` для edit/delete-синка** — in-memory dict, ограничен
  `KEEP_LAST_MANY=10000`, вытеснение FIFO по произвольному порядку dict,
  **теряется при рестарте** → синк правок/удалений ломается для старых
  сообщений после перезапуска. Это ровно то, ради чего у нас
  **персистентный реестр** (M1/M2). tgcf наглядно показывает цену
  отсутствия персиста.
- **`sys.exit()` в библиотечном коде** (`config.py`, `live.py`) —
  недопустимо для библиотеки; у нас ошибки конфигурации — исключения/
  fail-fast на границе.
- **`bare except`** (`storage.py:14`), широкий `except Exception` с
  проглатыванием (`past.py:84`) — наш стиль: узкие исключения, без
  глушения.

## Итог (для ADR и спеки M3)

1. **FloodWait/реконнект** — baseline Telethon (авто-реконнект + flood-порог)
   как фундамент; прикладной слой добавляет ретрай-после-сна **без
   пропуска** и **неблокирующий** троттлинг. Кода у tgcf не берём.
2. **Пагинация** — `iter_messages(reverse=True, offset_id=cursor)` +
   пропуск `MessageService`; курсор — наш транзакционный `CursorPort`.
   Берём семантику, механизм у нас лучше.
3. **Резолв сущностей** — однократный резолв в стабильный числовой id,
   ключевание по нему (валидирует наш `domain/keys`); добавить
   обработку ошибок резолва и **прогрев кэша сущностей** (gotcha
   холодного кэша, который tgcf обходит молча).
4. **Session string** — `StringSession` как опция, **но** зашифрованное
   хранение и генерация в CLI angarion. Файл-vs-StringSession для
   мультиаккаунта — вопрос к спеке T005.

Прямых заимствований кода (copy-paste фрагментов под атрибуцией) по итогам
ревизии **нет**: ценность tgcf — в подтверждении правильных примитивов
Telethon и в наглядных антипаттернах, а не в переиспользуемых кусках (что
ожидаемо при глобально-состоянийной архитектуре). Если на этапе T005
какой-то фрагмент всё же берётся дословно — помечается атрибуцией
`# Adapted from tgcf (MIT), https://github.com/aahnik/tgcf` прямо в коде.
