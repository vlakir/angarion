# Spec: Ядровое обобщение модели — `Record` + `transport` + capabilities

**Статус:** Analyzed
**Дата создания:** 2026-06-19
**Связанные документы:** `concepts/v2-multiformat-pipelines.md` (видение v2);
DECISIONS.md — ADR «Pivot к мультиформатным конвейерам» (2026-06-19);
зависимые задачи T037 (внутренний провод), T038 (ручной/веб запуск),
T039 (брокеры), T040 (email).

---

## 1. Overview

Фундамент волны v2: обобщить доменную модель ядра с «события сообщения
конкретного мессенджера» до **транспорт-агностичной записи (`Record`)**.
Сейчас модель и публичный контракт завязаны на мессенджер-понятия
(`messenger`, `chat_id`, событийная семантика new/edited/deleted как
обязательная). Чтобы подключать не-чат-источники/приёмники (брокеры, email,
далее произвольные) добавлением адаптера, а не правкой ядра, нужно:
вынести мессенджер-специфику в **опциональные capabilities адаптера**,
переименовать контракт в нейтральные термины (`transport`, `record`) и
сохранить всю v1-мессенджер-функциональность как частный случай. Это
крупный API-ломающий рефакторинг (допустимо в pre-alpha); на нём стоят
T039/T040.

## 2. User Stories / Сценарии использования

- Как **автор адаптера**, я хочу реализовать источник/приёмник для
  не-чат-транспорта (брокер, email), декларируя только те capabilities,
  которые он реально поддерживает (например, только `new`), чтобы ядро не
  навязывало мне модель правок/удалений и реестр, которых у транспорта нет.
- Как **автор адаптера мессенджера**, я хочу по-прежнему получать всю
  машинерию правок/удалений/catch-up/реестра, объявив соответствующие
  capabilities, чтобы поведение Telegram/Matrix не деградировало.
- Как **пользователь библиотеки**, я хочу единый контракт записи на входе и
  выходе независимо от транспорта, чтобы процессор и конфигурация
  пайплайна не зависели от того, чат это или очередь.
- Как **пользователь**, я хочу, чтобы существующие мессенджер-пайплайны
  продолжали работать после рефакторинга (с поправкой на переименования в
  публичном API, отражённые в CHANGELOG).

## 3. Functional Requirements

- ДОЛЖНА: ввести транспорт-агностичную доменную запись (`Record` — рабочее
  имя) как базовую сущность входа и выхода; «событие сообщения» становится
  её частным случаем/профилем.
- ДОЛЖНА: переименовать в публичной модели `messenger` → `transport`,
  message-ориентированные имена → `record`-ориентированные (точный список
  имён — в Clarify), сохранив семантику.
- ДОЛЖНА: ввести явную декларацию **capabilities адаптера** (например:
  `edits`, `deletes`, `history_fetch`/catch-up, `threads`, `media`, …);
  ядро активирует соответствующую машинерию (реестр, catch-up, поллинг
  окна) только для адаптеров, объявивших нужную capability.
- ДОЛЖНА: сохранить всю v1-функциональность для транспортов класса
  «мессенджер» (Telegram, Matrix) без регресса — правки/удаления,
  catch-up по реестру, лёгкий поллинг окна (T032), loop-guard.
- ДОЛЖНА: сохранить гарантии at-least-once + идемпотентность,
  дедупликацию, очередь, DLQ, аналитику в обобщённой модели.
- ДОЛЖНА: обновить порты (`ListenerPort`/source, `MessageSinkPort`,
  `ProcessorPort`, реестр, dedup) под обобщённые имена/типы и capabilities.
- ДОЛЖНА: обновить контрактные тесты `angarion.testing` под новую модель
  (это публичный инструмент для авторов адаптеров).
- ДОЛЖНА: при несовместимой подписке пайплайна (вид записи не объявлен в
  capabilities его transport — например `edited`/`deleted` у брокера) —
  **падать ошибкой валидации конфигурации на старте** (fail-fast), не
  warning+ignore.
- ДОЛЖНА: сменить публичные ключи конфига TOML под новую терминологию
  (`[accounts.*].messenger` → `transport`, `chat_id` в source/target →
  обобщённый `address`) **без обратной совместимости**; обновить
  существующие `app.toml`/примеры/доки в рамках задачи.
- ДОЛЖНА: зафиксировать ломающие изменения публичного API (включая
  `angarion.testing` и ключи конфига) в CHANGELOG; ADR на ключевые решения
  именования/структуры.
- НЕ ДОЛЖНА: вводить алиасы / переходную совместимость старых имён
  (решение big-bang) — старые имена удаляются, не сосуществуют с новыми.
- НЕ ДОЛЖНА: реализовывать конкретные не-чат-адаптеры (это T039/T040) —
  здесь только ядровой фундамент.
- НЕ ДОЛЖНА: вводить адаптеры произвольных данных (БД/файлы/S3/MQTT) —
  это горизонт видения, отдельные задачи по спросу.

## 4. Success Criteria

- Telegram- и Matrix-адаптеры работают на обобщённой модели **без регресса**
  поведения (все существующие тесты, включая интеграционные, зелёные).
- Адаптер, декларирующий только `new` (без правок/удалений/реестра),
  проходит конвейер end-to-end на InMemory/контрактных тестах, и ядро
  **не** активирует для него реестр/catch-up.
- Публичная модель использует `transport`/`record`-терминологию; в коде
  не осталось обязательной завязки ядра на «messenger/message».
- `mypy --strict` чист на пакете; coverage ≥ 90%; четыре pre-push проверки
  зелёные.
- Ломающие переименования отражены в CHANGELOG; ADR зафиксирован.

## 5. Key Entities

- **`Record`** (обобщение `InboundEvent`/`OutboundMessage`): происхождение
  (`transport`, адрес источника/назначения, идентификатор для дедупликации,
  время), полезная нагрузка (текст и/или структурированные данные,
  опциональные медиа/вложения), вид/семантика (для мессенджеров —
  new/edited/deleted; для прочих — только new), служебные поля
  (idempotency/dedup-ключи).
- **`Transport`** (обобщение `messenger`): идентификатор класса транспорта
  и его адресации (вместо `chat_id` — обобщённый адрес: chat/topic/
  queue/mailbox/…).
- **Capabilities адаптера**: декларативный набор поддерживаемых
  возможностей; вход для активации опциональной машинерии ядра.
- **Порты**: source/listener, sink, processor, registry, dedup, analytics —
  в обобщённой формулировке.

## 6. Assumptions & Constraints

- Проект pre-alpha — ломающие изменения публичного API допустимы,
  фиксируются в CHANGELOG/ADR.
- Гексагональная архитектура и набор гарантий (at-least-once,
  идемпотентность) сохраняются — меняется номенклатура и опциональность
  мессенджер-машинерии, не инварианты надёжности.
- Существует матрица возможностей мессенджеров (§12.10 CONCEPT v1) —
  capabilities-модель должна быть согласована/унифицирована с ней, а не
  ввести вторую параллельную.
- TDD обязателен; coverage ≥ 90%; `mypy --strict`.

## 7. Out of Scope

- Конкретные не-чат-адаптеры (брокеры — T039, email — T040).
- Адаптеры произвольных данных (БД/файлы/S3/MQTT/IoT).
- Внутренний провод (T037) и ручной/веб-запуск (T038) — отдельные задачи,
  опираются на этот фундамент.
- Горизонтальное масштабирование, новые форматы сериализации payload.

## Clarify (заполняется Claude)

### Open questions

- **Именование.** `Record` vs `Event` vs `Item` для базовой записи?
  `transport` vs `channel` vs `connector` для класса транспорта? Как
  назвать обобщённый адрес (вместо `chat_id`) — `address`/`endpoint`/
  `target`? Точный список переименований публичных типов/полей.
- **Структура записи.** Единый `Record` с опциональными полями для
  мессенджер-семантики, или базовый `Record` + профиль/подтип `MessageRecord`?
  Где живёт payload-полиморфизм (текст vs структурные данные) — одно поле
  `dict`/union, или типизированные варианты?
- **Capabilities — гранулярность и место.** Переиспользуем матрицу
  возможностей §12.10 (user_account/edit_events/delete_events/history_fetch/
  threads/push_transport) или вводим новую модель? Декларация — на уровне
  плагина адаптера (entry point), конфига, или рантайм-объекта?
- **Деградация при отсутствии capability.** Если пайплайн подписан на
  `edited`/`deleted`, а транспорт их не умеет — ошибка конфигурации на
  старте, предупреждение + игнор, или запрет подписки в схеме конфига?
- **Объём переименования в конфиге.** Меняем ли публичные ключи TOML
  (`[accounts.*].messenger`, `chat_id` в source/target) под новую
  терминологию, или конфиг остаётся обратносовместимым с алиасами?
- **Стратегия рефакторинга.** Одной задачей целиком или фазами (1: ввод
  `Record`/`transport` рядом со старым + алиасы; 2: миграция адаптеров;
  3: удаление старых имён)? Влияет на число PR и риск регресса.
- **Реестр/курсоры/dedup для не-мессенджеров.** Дедупликация остаётся
  обязательной для всех (нужен dedup-ключ у любого транспорта) — или тоже
  опциональна? Реестр сообщений — строго мессенджер-only?

### Resolved (с ответами)

- **Стратегия рефакторинга — big-bang (2026-06-19).** Обобщаем всё сразу,
  **без алиасов и переходного периода**. Реализация может дробиться на
  несколько PR по слоям (домен → порты → адаптеры → конфиг → тесты/примеры),
  но без параллельного сосуществования старых и новых имён. Опирается на
  pre-alpha. → влияет на §3 (убрана опция алиасов), §7.
- **Capabilities — расширяем существующую §12.10 (2026-06-19).** Не вводим
  вторую модель: обобщаем имеющуюся матрицу возможностей мессенджеров
  (`user_account`/`edit_events`/`delete_events`/`history_fetch`/`threads`/
  `push_transport`) до transport-агностичной; механизм деградации (§12.10)
  переиспользуется. → §3, §5 (capabilities), §6.
- **Деградация — fail-fast (2026-06-19).** Если пайплайн подписан на вид
  записи (например `edited`/`deleted`), который transport не объявил в
  capabilities, — **ошибка валидации конфигурации на старте**, не
  warning+ignore. Предсказуемость важнее гибкости. → §3 (новое требование),
  §4 (success criterion).
- **Ключи конфига — меняем чисто (2026-06-19).** Публичные ключи TOML
  меняются под новую терминологию (`[accounts.*].messenger` → `transport`,
  `chat_id` в source/target → обобщённый адрес), **без обратной
  совместимости**. Существующие `app.toml` и примеры обновляются в рамках
  задачи. → §3, §7 (примеры/доки в объёме).
- **Именование (дефолт, не блокер) — `Record` + `transport` + `address`.**
  Базовая запись — `Record` (как в видении v2); класс транспорта —
  `transport`; обобщённый адрес источника/назначения — `address`
  (вместо `chat_id`). Точные имена остальных полей фиксируются в Analyze/
  реализации; имена выбираются так, чтобы message-семантика читалась
  естественно.
- **Структура записи (дефолт) — единый `Record` с опциональными полями.**
  Один тип `Record` с опциональной message-семантикой (вид new/edited/
  deleted, previous-версия и т.п.), а **не** иерархия подтипов: проще для
  портов и сериализации. Payload — текст и/или структурированные данные +
  опциональные медиа.
- **Dedup и реестр (дефолт) — dedup обязателен для всех, реестр — мессенджер-
  only.** Дедупликация остаётся обязательной для любого транспорта (каждый
  даёт dedup-ключ из своего external_id — offset/message-id/Message-ID/…).
  Реестр сообщений с историей версий и catch-up по хэшам — capability класса
  «история/правки» (мессенджеры), активируется по объявленной capability.

## Analyze (заполняется Claude)

Перечитка spec после Clarify на противоречия/упущения/невозможности.

- 🔴 **Critical — миграция БД и существующие данные.** Переименование
  `messenger`→`transport` и обобщение адреса затрагивают персистентные
  схемы (реестр, аналитика, outbox, курсоры, сессии аккаунтов в `app.db`).
  Big-bang без алиасов требует **миграции Alembic** и решения по уже
  записанным данным (мигрировать значения столбцов vs принять разрыв на
  pre-alpha). Зафиксировать в реализации до правки моделей.
- 🔴 **Critical — объём «чистого» переименования каскадный.** `messenger`/
  `chat_id`/`message` пронизывают домен, порты, адаптеры (Telegram/Matrix/
  memory), конфиг, web-слой, контрактные тесты `angarion.testing`, примеры
  и доки. Big-bang = большой каскад; обязательно дробление на PR по слоям
  (домен+порты → адаптеры → конфиг/web → тесты/примеры/доки) при сохранении
  «без алиасов». Иначе один неподъёмный PR и риск долгой красной ветки.
- 🟡 **Warning — согласованность capabilities с матрицей §12.10.** Сейчас
  §12.10 описывает деградацию для мессенджеров. Обобщение должно
  переиспользовать её механизм, а не ввести параллельный; проверить, что
  fail-fast-валидация подписки ложится на существующий механизм деградации
  (возможно, §12.10 деградирует мягко — согласовать с новым fail-fast,
  не создать противоречие «деградируем тихо» vs «падаем на старте»).
- 🟡 **Warning — `angarion.testing` — публичный контракт.** Его изменение
  ломает сторонних авторов адаптеров. Для pre-alpha допустимо, но отразить
  в CHANGELOG как breaking и обновить документацию контракта.
- 🟡 **Warning — терминология «message»-процессоров и встроенных.**
  `passthrough`/`template`/`llm` и поля шаблона (`InboundEvent`-поля в доке
  §4) завязаны на message-имена; при обобщении проверить, не сломается ли
  публичный контракт `processor_config`/контекста шаблонов, и обновить доки.
- 🟢 **Note — `transport` как рабочее имя.** В видении зафиксировано как
  рабочее (альтернативы `channel`/`connector`). Финализировать одно имя в
  начале реализации, чтобы не переименовывать дважды.
- 🟢 **Note — порядок относительно T037–T040.** T041 — фундамент; T039/T040
  стартуют после него. T037/T038 от него прямо не зависят, но выиграют от
  обобщённой модели — брать после.

**Вердикт Analyze:** блокеров уровня «спека невозможна» нет; два Critical —
это требования к плану реализации (миграция БД + дробление по слоям), не
противоречия спеки. Спека готова к переходу в реализацию после фиксации
плана фаз. Статус можно поднимать до **Analyzed**.
