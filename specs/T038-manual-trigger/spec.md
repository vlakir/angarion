# Spec: Ручной запуск пайплайна (программный API + веб-API)

**Статус:** Implemented (2026-06-20, все 5 фаз)
**Дата создания:** 2026-06-20
**Связанные документы:** `BACKLOG.md` (T038), `CONCEPT.md` §12.5 (web read-only),
§12.9 (командный outbox / split-деплой), `DECISIONS.md` (ADR T024 — роли
процессов; ADR T037 — internal re-ingestion), `specs/T037-internal-wire/`.

---

## 1. Overview

Сейчас обработка инициируется **только** живыми событиями адаптеров-источников:
штатного «запусти сейчас / впрысни событие» нет. Веб-API сознательно read-only
(§12.5), а программная подача события (`IngestService.ingest`, `AngarionApp.ingest`)
внутренняя и недокументированная — собрать валидный `Record` руками нетривиально
(нужны `uid`, `dedup_key`, `source_key`, `idempotency_key`, `content_hash`).

T038 заводит **публичный, документированный ручной триггер** двумя путями:
**(1) программный API** — из пользовательского кода собрать событие из простого
payload (или подать готовый `Record`) и впрыснуть его в работающий конвейер;
**(2) веб-API** — HTTP-ручка приёма payload / запуска пайплайна, первое штатное
write-расширение помимо admin-управления пользователями. Оба пути работают и в
combined-, и в split-деплое (`--role api`), и снабжены UI-кнопкой в веб-морде.

## 2. User Stories

- Как **интегратор-разработчик**, я хочу из своего Python-кода подать событие
  (text + источник) в уже запущенный `AngarionApp` через документированный
  публичный метод, чтобы не реверсить внутреннее устройство `Record`.
- Как **оператор**, я хочу нажать кнопку «Запустить» в веб-морде и впрыснуть
  тестовое событие, чтобы проверить, что пайплайн доставляет, не дожидаясь
  реального сообщения в источнике.
- Как **внешняя служба / CI**, я хочу дёрнуть HTTP-ручку с API-ключом и
  идемпотентным ключом, чтобы инициировать обработку и безопасно ретраить при
  сетевом сбое без двойной обработки.
- Как **разработчик пайплайна**, я хочу прогнать конкретный payload через
  **именованный** пайплайн напрямую (минуя маршрутизацию по источнику), чтобы
  изолированно проверить его поведение.

## 3. Functional Requirements

**Программный API (публичный, документированный):**

- ДОЛЖНА: предоставить публичную **фабрику** «упрощённый payload → `Record`»
  (минимум: `text`, источник-`Endpoint`, `kind=new` по умолчанию; опц. медиа,
  `sender_*`, `event_at`, клиентский idempotency-ключ).
- ДОЛЖНА: предоставить публичный метод **впрыска события** на `AngarionApp`
  (семантика «event»: через `IngestService.ingest` → `router.resolve` →
  dedup/реестр/fan-out по конфигу), принимающий и упрощённый payload, и готовый
  `Record`.
- ДОЛЖНА: предоставить публичный метод **прямого запуска именованного пайплайна**
  (семантика «pipeline»: `QueueEnvelope(pipeline=name, record=…)` прямо в очередь,
  **минуя** dedup/реестр/router).
- ДОЛЖНА: экспортировать фабрику и типы payload из публичного `angarion` пакета.

**Веб-API:**

- ДОЛЖНА: HTTP write-ручка(и) для обоих путей (впрыск события / запуск
  именованного пайплайна), принимающая JSON-payload (упрощённый или полный
  `Record`).
- ДОЛЖНА: защищать write-ручку **отдельным API-ключом/токеном** (не admin-сессия
  fastapi-users); ключ конфигурируем, проверяется на каждый запрос.
- ДОЛЖНА: работать в **combined** (ручка зовёт `ingest`/очередь напрямую) и в
  **split** `--role api` (ручка кладёт команду в `CommandOutbox`, consumer
  pipeline-процесса исполняет — мост §12.9).
- ДОЛЖНА: добавить **UI-affordance** — минимальную форму/кнопку ручного триггера
  в веб-морде (под admin-сессией).

**Семантика и идемпотентность:**

- ДОЛЖНА: помечать ручные события `origin='manual'` (аналитика/трасса).
- ДОЛЖНА: принимать **опциональный** клиентский idempotency-ключ; при наличии —
  детерминированный `dedup_key` (ретрай гасится штатным dedup); при отсутствии —
  свежий `uid` (каждый вызов обрабатывается). **Дедуп по ключу — свойство
  event-пути** (он проходит `dedup.seen()`); прямой запуск пайплайна минует dedup
  (Q7/A2), поэтому идемпотентность там не гарантируется.
- НЕ ДОЛЖНА: ломать read-only-инвариант существующих `/api/v1`-ручек — write
  только на новых эндпойнтах под новой авторизацией.
- НЕ ДОЛЖНА: в split-режиме исполнять веб-триггер «в пустоту» — в `--role api`
  он обязан дойти до pipeline-процесса через outbox.

## 4. Success Criteria

- Из пользовательского кода событие подаётся в работающий конвейер одной
  публичной документированной строкой (payload → впрыск), без ручной сборки
  ключей `Record`.
- HTTP-ручка с валидным API-ключом инициирует обработку; без ключа/с неверным →
  `401`/`403`.
- Combined: впрыск через HTTP доезжает до доставки в M-получатель (e2e).
- Split (`--role api`): команда из api-процесса исполняется pipeline-процессом
  (контрактный/интеграционный тест на `CommandOutbox`-мост).
- Повторный HTTP-вызов с тем же idempotency-ключом не порождает второй обработки
  (dedup); без ключа — порождает.
- Прямой запуск именованного пайплайна стейджит `QueueEnvelope` ровно для
  указанного пайплайна, минуя router/dedup.
- Ручные события видны в аналитике с `origin='manual'`.
- UI: кнопка/форма триггерит обработку под admin-сессией.
- coverage ≥ 90%; четыре pre-push проверки чисты; `mypy --strict` чист.

## 5. Key Entities

- **`Record`** (существует) — нормализованная запись. Ручной впрыск строит её из
  payload; `origin='manual'`, `received_by`/`source` из payload.
- **ManualEvent payload** (новый, упрощённый DTO) — пользовательский ввод: `text`,
  источник (`transport`/`address`/`thread_id`), опц. `kind`, медиа, `sender_*`,
  `event_at`, `idempotency_key`. Фабрика разворачивает его в `Record`.
- **`QueueEnvelope`** (существует) — для прямого запуска именованного пайплайна.
- **`OutboxCommand` / `CommandKind`** (существует, §12.9) — расширяется новым
  видом(ами) для split-моста: команда несёт payload (упрощённый или
  сериализованный `Record`) + целевую семантику (event/pipeline).
- **API-ключ** (новый) — конфигурируемый секрет; FastAPI-зависимость авторизации
  write-ручки.

## 6. Assumptions & Constraints

- Pre-alpha: ломающие изменения сериализации/конфига допустимы без миграции
  данных (как T037/T041/T043), фиксируются в CHANGELOG.
- API-ключ — секрет; в репозиторий не попадает (env / `.secrets`, §«Гигиена»).
  В split-деплое проверка ключа происходит в api-процессе (у него нет конвейера).
- `origin` уже расширяемое поле (значения `live`/`catchup`/`internal`); добавляем
  `manual`.
- Очередь и `CommandOutbox` сериализуют payload как JSON (in-flight), новые поля
  аддитивны — чистый разрыв формата без БД-миграции (как T037 A4).
- Прямой запуск именованного пайплайна предполагает, что имя существует в конфиге;
  неизвестное имя → ошибка валидации (HTTP `422` / исключение в программном API).

## 7. Out of Scope

- Управление пайплайнами помимо ручного триггера (пауза/стоп/редактирование
  конфига через web) — остаётся вне v1 (§12.5).
- Расширенный планировщик/cron ручных запусков — отдельная задача при
  необходимости.
- Батч-впрыск множества событий одним запросом — MVP принимает одно событие на
  вызов (петля на стороне клиента).
- Edited/deleted через ручной триггер за пределами `kind`-поля payload — семантика
  правок/удалений руками не специфицируется глубже, чем «kind прокидывается».

## Analyze (заполняется Claude, 2026-06-20)

Перечитаны spec + plan против кода. Чистого прохода добивались правкой плана
(A1 ниже упростил мост). Остаточных Critical нет.

### 🔴 Critical — закрыть до реализации (решены в плане)

- **A1 — split-мост: только event-путь, pipeline-путь через общий `queue`.**
  Изначально план закладывал два `CommandKind` (event + pipeline). Но api-процесс
  **уже** пишет в общий `queue.db` напрямую: `requeue_dead_letter` делает
  `queue.put` (`http/ops.py:171`) — установленный паттерн. Значит «прямой запуск
  именованного пайплайна» (сырой `QueueEnvelope`) идёт через `queue.put` и в
  combined, и в split — **без** команды outbox. Через `CommandOutbox` нужен лишь
  **event**-путь (ему требуется `IngestService` с router/dedup/реестром, а он
  живёт только в pipeline-процессе). **Итог: один новый `CommandKind` = `INJECT`**
  (event-семантика); pipeline-путь — `queue.put` везде. План обновлён.

### 🟡 Warning — учесть при реализации

- **A2 — idempotency-ключ влияет только на event-путь.** dedup проверяется внутри
  `IngestService.ingest` (event). Прямой запуск пайплайна (Q7) **минует** dedup,
  поэтому клиентский idempotency-ключ там не подавляет повтор — ретрай pipeline-
  пути всегда обрабатывается заново. Зафиксировано в FR (ниже уточнено): дедуп по
  ключу — свойство event-пути; pipeline-путь идемпотентность не гарантирует.
- **A3 — фабрика вычисляет `content_hash` из текста.** `make_dedup_key(NEW)` не
  требует `content_hash`, но `EDITED` — требует. Ручной триггер с `kind=edited`
  валиден только если фабрика считает `content_hash` через
  `normalize_and_hash(text)`. Фабрика делает это при наличии текста; `kind=deleted`
  без текста допустим (del-ключ). MVP-дефолт `kind=new` обходит вопрос.
- **A4 — UI-форма доступна лишь при `api.auth="users"`.** UI-affordance (фаза 4)
  опирается на admin-сессию fastapi-users; при `auth="none"` admin-сессии нет →
  формы нет. Машинная HTTP-ручка (API-ключ) от режима auth **независима**. В доках
  явно: UI-кнопка требует `auth="users"`; программный путь и ключ-ручка — нет.
- **A5 — место фабрики: `application`, не `domain`.** Сборка `Record` тянет
  `received_at = now()` (нечистая, часы) и валидацию имени пайплайна по конфигу —
  это оркестрация. Фабрика живёт в `application` (часы инъектируемы/дефолт
  `datetime.now(UTC)`), используя чистые `domain/keys`. Согласуется с §14.9.

### 🟢 Note — к сведению

- **A6 — `trace_id` ручной записи** = `str(uid)` через существующий валидатор
  (`models.py:172`) — корень собственной трассы, консистентно с live/catchup.
- **A7 — оба пути строят `Record`.** Даже pipeline-путь оборачивает `Record` в
  `QueueEnvelope`, поэтому фабрика — общий фундамент обоих путей и обоих API.
- **A8 — `AngarionDeps += ingest: Any = None`.** combined несёт `ingest` (из
  `AngarionApp`), api-роль — `None`; роут диспетчеризует по наличию. `queue` в
  deps уже есть (используется requeue).
- **A9 — worker downstream использует `record.dedup_key`** для idempotency-ключей
  исходящих, поэтому валидный `dedup_key` обязателен и на pipeline-пути (фабрика
  его проставляет) — даже хотя сам dedup не проверяется.
- **A10 — пути HTTP** под `/api/v1` (write рядом с read) — допустимо, фиксируем в
  гайде; alt `/api/v1/manual/*` косметичен.
