# Пример: цепочка пайплайнов через «внутренний провод»

Два независимых пайплайна, связанных **напрямую** — выход одного становится
входом другого, минуя реальную платформу:

```
группа A ──(stage1: нормализатор)──▶ internal:stage1 ──(stage2: оформитель)──▶ группа B
```

Раньше такую связку можно было собрать только через служебную
группу-посредник X (stage1 пишет в X, stage2 слушает X) — ценой лишнего
трафика, задержки через Telegram, видимого служебного чата и
неотлавливаемого межпайплайнового цикла. **Внутренний провод** (T037)
соединяет пайплайны без выхода наружу: исходящая запись первого пайплайна
через синтетический транспорт `internal` подаётся обратно на вход (re-ingestion).

Демонстрирует:

- разбиение обработки на **независимые звенья-пайплайны** (каждое со своим
  процессором), вместо одного монолитного процессора;
- стык звеньев по совпадению `(transport=internal, address)` у `target`
  одного и `source` другого пайплайна;
- сквозную трассировку: на выходе доступен `origin=internal` (маркер
  «пришло по проводу», рядом с `live`/`catchup`).

## Как это устроено в [`app.toml`](app.toml)

- `[accounts.wire]` с `transport = "internal"` — объявляет внутренний
  транспорт. Секретов, сессии и авторизации ему не нужно: наружу он не ходит.
- **stage1** (`template` → `[norm] {{ text }}`): источник — группа A
  (Telegram), цель — `{ account = "wire", address = "stage1" }`. Наружу
  ничего не шлёт — кладёт результат во внутренний канал `stage1`.
- **stage2** (`template`): источник — тот же внутренний канал
  `{ account = "wire", address = "stage1" }`, цель — группа B (Telegram).
- `[chains] max_hops` — рантайм-лимит прыжков по внутренним рёбрам
  (backstop против циклов; дефолт 10).

Канал `stage1` — произвольное имя; ребро цепочки определяется именно
совпадением канала между `target` stage1 и `source` stage2.

## Что нужно

- Установленный проект с extra: `uv sync --extra telegram --extra sqlite`
  (или `uv add "angarion[telegram,sqlite]"` во внешнем проекте). Внутренний
  транспорт `internal` встроен — отдельного extra не требует.
- Telegram-аккаунт, **состоящий в обеих группах** A и B.
- `api_id` / `api_hash` — с <https://my.telegram.org> → API development
  tools (или официальные TDesktop-ключи).
- `id` групп (вида `-100…`) — узнать можно, например, переслав сообщение
  из группы боту `@username_to_id_bot`, либо из клиента.

## Настройка

1. Подставь `id` групп в [`app.toml`](app.toml): группу A — в `sources`
   звена `stage1`, группу B — в `targets` звена `stage2`.
2. Задай секреты в окружении (не в файлах — они не должны попасть в git):

   ```bash
   export ANGARION_ACCOUNTS__MAIN__API_ID=12345
   export ANGARION_ACCOUNTS__MAIN__API_HASH=0123456789abcdef0123456789abcdef
   ```

## Запуск

```bash
examples/chain/run.sh
```

Скрипт «всё в одном» (идемпотентный): применяет миграции БД, добывает
сессию аккаунта `main` (dev — из env-`StringSession`; внешний пользователь —
интерактивный `angarion login` при первом запуске), запускает конвейер.
Подробности шагов сессии — как в [`examples/forward`](../forward/README.md).

Проверка: после старта напиши в группу A — текст пройдёт `stage1` →
внутренний провод → `stage2` и прилетит в B с пометкой
`✅ обработано (internal)`. `Ctrl+C` — корректная остановка.

Весь рантайм (БД, ключ, сессия) — в `angarion-data/` рядом со скриптом;
этот каталог в `.gitignore`, секреты в репозиторий не попадают.

## Топология в Web UI

Запусти параллельно web-морду (см. [`examples/web`](../web/README.md)) и
открой `/ui/pipelines`: цепочка рисуется ребром `stage1 → stage2` (внутренний
канал схлопнут в одно ребро pipeline→pipeline и визуально отличим от обычных
source/target), а не двумя несвязанными пайплайнами.

## Заметки

- **Звеном может быть любой процессор.** Здесь оба звена — `template` (без
  внешних зависимостей, пример самодостаточен). Замени, например, `stage2` на
  `llm` (extra `angarion[llm]`, см. [`examples/digest`](../digest/README.md)) —
  получишь «нормализатор → LLM-обогатитель → доставка».
- **Только `new`.** Внутренний транспорт декларирует capability `new`:
  re-ingested запись всегда `new`. Если `stage1` реагирует на
  `edited`/`deleted`, на внутреннем ребре это всё равно `new` (проброс
  правок сквозь провод — вне MVP). Подписка `stage2` на `edited`/`deleted`
  отклоняется на старте (внутренний транспорт их не умеет).
- **Защита от циклов двухуровневая.** Циклическую цепочку (`stage1 →
  stage2 → stage1`) конфиг отклоняет на старте (fail-fast DAG-валидация).
  Цикл через реальную платформу стартовая проверка не видит — его ловит
  рантайм-лимит `max_hops` (запись уходит в DLQ с пометкой).
- **At-least-once без дублей.** Ключи стыка детерминированы из
  `idempotency_key` исходящей записи: повторная доставка внутреннего ребра
  (ретрай outbox) гасится штатным дедупом на входе stage2 — дубля нет.
- **Split-деплой.** Re-ingestion идёт через очередь (`EventQueuePort`):
  звенья могут жить в разных процессах (`--role api` / `pipeline`). Для
  боевого split-режима — `queue.backend = "persistqueue"`.
