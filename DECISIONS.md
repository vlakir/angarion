# Architecture Decisions

ADR-Lite: компактный лог архитектурных решений с обоснованиями.
Цель — через полгода можно ответить на вопрос «а почему мы тогда так
сделали?», не реконструируя контекст по коммитам.

## Формат

Каждое решение — короткий блок:

- **Дата** — когда принято.
- **Решение** — что решили (1 строка).
- **Контекст** — какая задача / ограничение к нему привели.
- **Альтернативы** — что рассматривали и почему отвергли.
- **Последствия** — что это нам теперь даёт и чего лишает.

Решения не редактируются после фиксации. Если решение пересмотрено —
добавляется новый блок со ссылкой на старый, старый помечается как
«Заменено решением от <дата>».

## Пример (удалить при заполнении шаблона)

### 2026-05-13 — SQLite вместо PostgreSQL для MVP

- **Контекст:** проект для одного пользователя, < 10 МБ данных, нужен
  быстрый запуск без отдельного сервиса.
- **Альтернативы:**
  - PostgreSQL — отвергли, нет резона держать отдельный процесс ради
    одного пользователя; миграцию делать всегда успеем.
  - JSON-файл — отвергли, теряем транзакционность и индексы.
- **Последствия:** деплой = один бинарь, бэкап = копия файла. При росте
  > 100 МБ или появлении конкурентного доступа — пересмотреть.

### 2026-06-16 — Шов логина в контракте плагина: `make_login` на `AdapterPlugin` (T010, M7 фаза B1)

- **Решение:** интерактивный логин (`angarion login`) перенесён из
  `cli.py` в контракт плагина — у `AdapterPlugin` появилось аддитивное
  поле `make_login: LoginFactory | None = None` (`LoginFactory =
  Callable[[LoginContext], Awaitable[None]]`). Плагин получает
  `LoginContext` (имя аккаунта, провалидированный account-config,
  **непрозрачный** `SessionStorePort`, ключ шифрования), сам выполняет
  платформенный обмен (пароль/код → сессия) и персистит её своим
  at-rest-декоратором. `cmd_login` стал платформо-агностичным: резолвит
  плагин по `messenger` аккаунта и делегирует. `None` — платформа без
  логина (InMemory) → `ConfigError`. Telegram перевёл свой
  `login_and_export_session` в `make_login`, не меняя поведения.
- **Контекст:** до B1 `cmd_login` был зашит под Telegram
  (`TelegramAccountConfig` + `StringSession`). Matrix-логин принципиально
  иной (homeserver/пароль → `access_token`+`device_id`), и ветвление по
  платформам в CLI разнесло бы платформенное знание по ядру/драйверу.
  Логин — такая же платформенная забота, как приём/отправка, поэтому шов
  лёг на плагин рядом с `make_listener`/`make_sender` (§12.11). Решение
  Владимира 2026-06-16 (развилка «login-шов»).
- **Альтернативы:**
  - Ветка по `messenger` внутри `cli.py` — отвергли: знание о
    платформенном логине размазано по CLI, контракт плагина неполон.
  - Возвращать из `make_login` строку сессии, шифровать/сохранять в CLI —
    отвергли: тогда CLI должен знать, **каким** декоратором шифровать
    (телеграм vs matrix), что снова тащит платформенное ветвление; проще
    отдать персист самому плагину (он владеет своей криптой).
- **Последствия:** добавление платформы с логином не трогает CLI/ядро —
  только новый `make_login` в плагине. Сетевой/интерактивный шов внутри
  плагина (`login_and_export_session` / `password_login`) — инъецируемый
  module-level seam, юнит-тестируется подменой без сети. Поле
  опционально — существующие плагины (memory) и сторонние не ломаются.

### 2026-06-16 — Matrix-каркас: полный профиль capabilities, сессия в `app.db`, своя крипта, базовый nio (T010, M7 фаза B1)

- **Решение:** заведён пакет `adapters/matrix/` (extra `angarion[matrix]`,
  entry point `angarion.adapters:matrix`) как **каркас** второго боевого
  адаптера. В B1: матрица возможностей `MATRIX_CAPABILITIES` (полный
  профиль — `user_account`/`edit_events`/`delete_events`/`history_fetch`/
  `threads` = True, `push_transport="client"`); схема
  `MatrixAccountConfig` (`homeserver`/`user_id`/`device_name`, пароль —
  **не** в модели); парольный `make_login` (`AsyncClient.login` → токен +
  `device_id`). Решения по узлам:
  - **Сессия Matrix в `app.db`** через `SessionStorePort` как непрозрачная
    `MatrixSession` (JSON: homeserver/user_id/device_id/access_token),
    зашифрованная Fernet — как Telegram (ADR 2026-06-13). E2EE key-store
    (olm/megolm) — отдельный sqlite на ФС в B2, в эту строку не входит.
  - **Своя крипта в `matrix/session.py`** (`MatrixEncryptedSessionStore`)
    — Matrix не импортирует декоратор из telegram-адаптера. Соответствует
    задокументированному замыслу «крипта — забота адаптера платформы»
    (ADR 2026-06-13); фаза изолирована, telegram не трогаем. Цена —
    дублирование ~50 строк Fernet-обёртки.
  - **Базовый `matrix-nio` без `nio[e2e]`** в B1: login через
    `AsyncClient.login` токен/device не требует olm. Инициализацию
    E2EE-стора (`store_path`/`AsyncClientConfig`) и саму расшифровку
    откладываем в B2 (там же — системная libolm). B1 не упирается в
    libolm-сборку в dev-окружении.
  - **`make_listener`/`make_sender` — fail-fast-заглушки** (`NotSupported
    Error`, «реализуется в B2/B3»): плагин обязан грузиться из entry point
    (иначе `angarion login` не резолвит платформу), но pipeline в B1 ещё
    нечем собрать. Сигнатуры фабрик постоянны — в B2/B3 наполняется тело.
- **Контекст:** Matrix — кандидат №1 на доказательство переносимости
  портов (§12.10); реализуется фазами B1–B5 под зонтиком T010. Развилки
  закрыты Владимиром 2026-06-16 (login-шов / сессия-крипта / E2EE-сейчас).
- **Альтернативы:** вынести `EncryptedSessionStore` в общий модуль (DRY) —
  отвергли в пользу изоляции фазы (не трогаем telegram, меньше blast
  radius B1); `nio[e2e]` сразу — отложили (libolm-риск, расшифровки всё
  равно нет до B2); не регистрировать entry point до B2 — отвергли (login
  не нашёл бы плагин).
- **Последствия:** `angarion login --account <matrix>` работает с B1;
  приём/отправка Matrix — fail-fast до B2/B3. Профиль capabilities виден
  в `/ui/diagnostics` (механизм M5). Контрактные наборы портов и
  E2EE-расшифровка — B2.

### 2026-06-16 — Медиа-политика: глобальная `[media]`, скачивание при ingest принимающим аккаунтом (T010, M7 фаза A3, срез 3)

- **Решение:** введена **глобальная** секция `[media]` (`MediaConfig`):
  `download` (по умолчанию `False`), `allowed_kinds` (пусто = все),
  `max_size` (0 = без лимита), `storage_dir` (`data/media`, git-ignored),
  `retention_days` (0 = бессрочно). Предикат «качать ли» — метод
  `MediaConfig.should_download(media)` (messenger-agnostic). Скачивание
  выполняет **принимающий аккаунт** при ingest — хук `enrich_with_downloads`
  в Telegram-адаптере (live `_emit` listener'а + catch-up `_emit_messages`):
  по политике рефетчит источник новым методом порта `download_media` и
  проставляет `MediaRef.local_path`. Sender при наличии `local_path` грузит
  файл напрямую (`send_media(local_path=…)` → `send_file` по пути) — это и
  даёт кросс-аккаунт/кросс-платформа доставку; без `local_path` остаётся
  refetch-fast-path A2. Ретеншн файлов — отдельный шаг фоновой prune-задачи
  (`AngarionApp._prune_media`, по mtime, §17.3).
- **Контекст:** A3 замыкает медиа-часть — нужна управляемая политика
  скачивания/хранения и кросс-аккаунтная доставка (когда refetch-fast-path
  недоступен). Resolved Q2/Q4/Q6.
- **Альтернативы:**
  - **Per-pipeline переопределение политики** (Resolved Q3) — **отложено**
    (решение Владимира 2026-06-16, → BACKLOG T033). Download физически
    account/source-level (до fan-out в пайплайны), поэтому per-pipeline knob
    — это не «скачивать ли», а «пересылать ли медиа в этом пайплайне»
    (send-time concern уровня `passthrough`/sender). В A3 — только глобальная
    политика; гранулярность пересылки — отдельной задачей.
  - Скачивание в application-`IngestService` (messenger-agnostic) — отвергнуто:
    рефетч/скачивание требуют платформенного клиента; ingest клиента не
    держит. Хук живёт в адаптере, ядро не трогаем.
  - `MediaStorePort` (абстракция ФС/S3) — отложено (Resolved Q6): для v1
    хватает файлового каталога; S3 — последующим аддитивом.
  - `download_media` без `to_thread` (синхронный `Path.mkdir`) — отвергнуто
    (ruff ASYNC240): создание каталога offload'ится в `asyncio.to_thread`,
    event loop не блокируется.
- **Последствия:** медиа сквозь пайплайн доходит кросс-аккаунт (через
  скачанный файл), процессоры получают `local_path`; по умолчанию диск не
  растёт (download opt-in, fast-path по ссылке). Скачивание при catch-up —
  best-effort, сбой границы (FloodWait/transient) деградирует до «только
  метаданные», событие не теряется. **A3 закрыт; дальше A4** (README/
  CHANGELOG/DECISIONS + пример зеркала с медиа).

### 2026-06-16 — Media-хэш в реестре: catch-up-детекция медиа-правок (T010, M7 фаза A3, срез 2)

- **Решение:** `media_hash` хранится в реестре (`RegistryRecord`,
  `RegistryVersion`, ORM-колонки + миграция 0006) и несётся на
  `InboundEvent`. Детектор изменений (`registry_rules.content_unchanged`,
  общий для memory и SQLite — SC-4) и catch-up (`_emit_messages`,
  `raw_media_hash`) сравнивают **и** текстовый, **и** медиа-хэш. Исход
  `RegistryOutcome.TEXT_CHANGED` теперь означает «содержимое (текст и/или
  медиа) изменилось».
- **Контекст:** срез 1 закрыл live-правки медиа через дедуп-ключ, но
  catch-up-сверка сравнивала только `content_hash` → подмену вложения за
  простой проморгал бы. Этот срез доводит детекцию до catch-up.
- **Альтернативы:**
  - Хэш в `content_hash` вместо отдельного поля — отвергнуто (Analyze):
    text-`content_hash` неприкосновенен (нет миграции старых записей).
  - Новый исход `MEDIA_CHANGED` — отвергнуто: `TEXT_CHANGED` уже драйвит
    `previous_text`-обогащение; расширение его смысла дешевле нового члена
    enum'а и не трогает потребителей.
- **Последствия:** медиа-правки ловятся и live, и в catch-up; миграция
  `media_hash` — nullable, без бэкафилла (старые строки = NULL = «медиа
  неизвестно»: первый catch-up после апгрейда может счесть медиа-сообщение
  правкой один раз — само-залечивается). **Остаётся в A3:** политика
  скачивания/хранения + скачивание-fallback кросс-аккаунта (срез 3).

### 2026-06-16 — Media-хэш в дедуп-ключе правок (T010, M7 фаза A3, срез 1)

- **Решение:** edit-детекция учитывает вложения. `make_media_hash(media)` —
  SHA-256 опознающих метаданных (kind/mime/имя/размер/размерности/
  длительность), `make_dedup_key` получает параметр `media_hash`. Слот версии
  ключа `MESSAGE_EDITED` (`_edit_slot`): текст-без-медиа → `content_hash`
  (ключ прежний); медиа-only → `media:<hash>`; текст+медиа → комбинированный
  хэш.
- **Контекст:** M7, Resolved Q5 («подмена вложения при том же тексте =
  EDITED») + must-fix, найденный в A2: медиа-only `MESSAGE_EDITED`
  (`text=None`) падал в `make_dedup_key` (для EDITED был обязателен
  `content_hash`).
- **Альтернативы:**
  - Свернуть медиа в `content_hash` (Resolved Q5 буквально) — отвергнуто в
    пользу Analyze-уточнения: text-`content_hash` оставлен нетронутым (golden
    §7.2 для текста байт-в-байт прежний, нет миграции text-only записей
    реестра); медиа влияет только на слот ключа EDITED.
  - Контент-хэш по байтам файла — отвергнуто: требует скачивания (против
    fast-path-дефолта). Хэшим метаданные; два разных файла с идентичными
    метаданными неотличимы — приемлемый компромисс.
  - `ref`/`local_path` в отпечатке — исключены сознательно: `ref` постоянен
    в пределах сообщения (координаты источника), `local_path` — доставка.
- **Последствия:** медиа-only правки не падают; подмена файла ловится как
  правка; контракт §7.2 для текста не меняется (аддитивно, golden зелёные).
  Цена — **однократный** транзиент при апгрейде: для text+медиа сообщений,
  отредактированных в окне дедупа до апгрейда, ключ EDITED пересчитается
  (`content_hash` → комбинированный), возможна одна повторная доставка;
  само-залечивается. **Не сделано в этом срезе** (следующие срезы A3):
  хранение `media_hash` в реестре для catch-up-детекции медиа-only правок,
  политика скачивания/хранения, скачивание-fallback кросс-аккаунта.

### 2026-06-16 — Пересылка медиа Telegram: refetch по координатам источника (T010, M7 фаза A2)

- **Решение:** sender пересылает вложение **без скачивания** — рефетчит
  исходное сообщение аккаунтом-отправителем по координатам
  `MediaRef.ref = "chat_id:message_id"` (`get_messages`) и шлёт его медиа
  (`send_file`) с подписью. Источник недоступен/удалён → деградация до
  текстовой отправки (сообщение не теряется, медиа — да).
- **Контекст:** M7 A2, fast-path-доставка медиа (resolved «fast-path без
  скачивания»). В MTProto нет переносимого `file_id` (это Bot API); резенд
  идёт через объект медиа исходного сообщения.
- **Альтернативы:**
  - Сериализовать file handle (`id`+`access_hash`+`file_reference`) в `ref` —
    отвергнуто: `file_reference` протухает (минуты–часы), в очереди с
    ретраями/задержкой отправка сыплется `FILE_REFERENCE_EXPIRED`, а
    восстановление всё равно требует рефетча → выбрали рефетч сразу.
  - Скачивание-then-reupload по умолчанию — отвергнуто как дефолт (диск/
    трафик, противоречит resolved); остаётся **fallback** для кросс-аккаунта
    в A3.
- **Последствия:** пересылка медиа из коробки для зеркала на одном аккаунте
  (отправитель имеет доступ к источнику — типовой кейс), `ref` крошечный и
  сериализуемый, диск не растёт. Ограничение: кросс-аккаунт (отправитель не
  в источнике) сейчас деградирует до текста — скачивание-fallback запланиров.
  на A3. `ref`-формат — adapter-owned, парсит тот же Telegram-sender.

### 2026-06-16 — `InboundEvent.has_media` — `@property`, а не `@computed_field` (T010, M7 фаза A2)

- **Решение:** `has_media` производится от `media` обычным `@property`
  (`return bool(self.media)`), а не pydantic `@computed_field`. Следствие:
  доступ `event.has_media` сохранён, но поле **не сериализуется** в
  `model_dump`/JSON (значение тривиально выводится из `media`, который
  сериализуется).
- **Контекст:** M7 A2 убирает булево поле `has_media` в пользу
  производного от структурного `media`. `@computed_field` над `@property`
  даёт ошибку mypy `[prop-decorator]` без pydantic-плагина mypy.
- **Альтернативы:**
  - `@computed_field` + `# type: ignore[prop-decorator]` — отвергнуто:
    проектное правило запрещает `type: ignore` без обсуждения, а городить
    подавление ради косметики сериализации не стоит.
  - Включить `plugins = ["pydantic.mypy"]` в `[tool.mypy]` — отложено: это
    project-wide изменение поведения тайпчекера, отдельное осознанное
    решение (обсудить, если появится потребность в сериализуемых
    computed-полях). Пока ни одно поле этого не требует.
- **Последствия:** ноль `type: ignore`, ноль config-изменений, mypy
  --strict зелёный. Цена — `has_media` не в JSON-дампе события; на
  поведение не влияет (ни один потребитель не читает его из сериализованного
  payload — проверено grep'ом), при необходимости вернуть в дамп —
  включить pydantic-плагин и заменить на `@computed_field`.

### 2026-06-16 — `MediaRef` + аддитивное поле `media`, транзит в passthrough (T010, M7 фаза A1)

- **Решение:** введён доменный DTO `MediaRef` (открытый строковый `kind`;
  `ref` — непрозрачная платформенная ссылка для пересылки без скачивания;
  опц. mime/имя/размер/размерности/длительность; `local_path` — при
  скачивании по требованию). Добавлены аддитивные поля
  `InboundEvent.media: list[MediaRef]` и `OutboundMessage.media`
  (default `[]`). `passthrough` переносит `event.media` в каждый
  `OutboundMessage` транзитом.
- **Контекст:** M7, часть A (медиа). §17.8.2 заранее санкционирует медиа как
  аддитивное минорное изменение. Фаза A1 — только доменная обвязка и транзит;
  извлечение реальных вложений из Telethon и их отправка — фаза A2.
- **Альтернативы:**
  - `has_media` → `@computed_field` **уже в A1** (как планировалось в
    Clarify) — отвергнуто на реализации: в A1 Telegram ещё не рождает
    структурный `media`, поэтому пришлось бы либо плодить throwaway-placeholder
    (`MediaRef(kind='unknown')`), либо потерять сигнал `has_media` на время
    между A1 и A2. Флип `has_media` → computed перенесён в **A2**, где
    Telegram-маппинг отдаёт реальный `media`. Уточнение последовательности,
    не изменение scope; `has_media: bool` пока остаётся полем.
  - Медиа через `OutboundMessage.extra` (нетипизированный dict) — отвергнуто:
    отдельное типизированное поле чище и проверяется mypy.
  - Включить медиа-отпечаток в `content_hash`/`idempotency_key` сейчас —
    отложено в A3 (edit-детекция по медиа). В A1 `idempotency_key` **не
    меняется**: он строится по `dedup_key` (несёт `external_id`), поэтому
    разные сообщения — в т.ч. медиа-only с пустым текстом — не коллидируют;
    публичный контракт §7.3 не трогаем.
  - Релаксация DROP в passthrough для медиа-only (`text=None`, непустой
    `media`) — отложена в A2: без поддержки медиа на стороне sender'а это
    породило бы отправку пустого текста.
- **Последствия:** домен готов принимать структурные вложения от адаптеров
  (A2/B) и переносить их по пайплайну; изменение полностью обратно-совместимо
  (поля с дефолтами, JSON-roundtrip и `extra=forbid` держатся), покрытие

### 2026-06-16 — `connect_client`: `get_me` + `catch_up` — робастность приёма live (T030, всплыло в M6)

- **Решение:** `connect_client` после `client.connect()` вызывает
  `await client.get_me()` и `await client.catch_up()` (до подписки
  listener'а) — для реконсиляции update-state свежеподключённого клиента.
- **Контекст:** прод хранит сессии как зашифрованный `StringSession`
  в `app.db` (ADR 2026-06-13). `StringSession` **не кэширует self и не
  персистит per-channel `pts`** — свежеподключённый клиент принимает
  live-апдейты не сразу; `get_me`+`catch_up` форсирует выравнивание.
  Всплыло при отладке контура M6. **Важно — это НЕ подтверждённый
  блокирующий прод-баг:** диагностикой показано, что **входящие** live от
  других в активных группах (основной прод-сценарий — зеркалирование
  чужих сообщений) приходят и без этого; ненадёжным оказался лишь приём
  **собственного исходящего** (self-send) в тихую супергруппу — артефакт
  одно-аккаунтного тест-драйва (per-channel `pts` gap), а не боевого пути.
  Поэтому правка — улучшение робастности начального приёма, не аварийный
  фикс. Первоначальный вывод «прод-баг» снят как переоценённый.
- **Альтернативы:**
  - `client.start()` вместо `connect()` — отвергнут: тянет sign-in-флоу
    (в headless-раннере нежелателен), а нужна лишь реконсиляция.
  - Не делать ничего — допустимо (основной сценарий работал), но
    `get_me`+`catch_up` дёшевы и делают приём после старта предсказуемее.
- **Последствия:** приём live после старта/простоя предсказуемее.
  Реконсиляция идёт **до** подписки listener'а — пропущенное за простой
  поднимает app-level catch-up §9.3. Интеграционный контур M6 на live
  self-send **не опирается** (ненадёжно): new/edited/deleted сквозь
  пайплайн проверяются через catch-up §9.3 (history-реконсиляция,
  `iter_messages` — детерминирована, без `pts`-хрупкости).

### 2026-06-16 — Петлевой guard `source == target` через dedup-пометку произведённых сообщений (T009, M6, фаза 1)

- **Решение:** когда цель пайплайна совпадает с прослушиваемым
  источником, петля собственных доставок гасится декоратором
  `MessageSinkPort` — `LoopGuardSink` (`application/loop_guard.py`).
  После успешной доставки он помечает в `DedupStorePort` будущий
  `dedup_key` произведённого сообщения (NEW и DEL по
  `DeliveryReceipt.external_id`), и `IngestService` отбрасывает его
  возврат (live или catch-up) как `duplicate`. Подключается в
  `build_app` только при наличии совпадения цели с источником (иначе
  no-op). Messenger-agnostic, новых портов/таблиц нет — маркеры живут в
  персистентном dedup (переживают рестарт, попадают под общий `prune`).
- **Контекст:** §13.2 требует сценарий `source == target` (вариант 2
  топологии M6). Без guard'а доставленное в источник сообщение
  возвращается как новое и зацикливается. Фильтр по `sender_id`
  («не обрабатывать свои сообщения») отвергнут: интеграционный контур
  self-driving — драйвер пишет тем же аккаунтом, что и пайплайн, и
  такой фильтр отсёк бы и сообщения драйвера.
- **Альтернативы:**
  - Sender-based фильтр по `sender_id` — отвергнут (конфликт с
    self-driving, см. выше).
  - Новый персистентный порт «реестр произведённых id» — отвергнут:
    `DedupStorePort` уже даёт ровно нужную семантику (персистентность +
    `prune`), дублировать незачем.
- **Последствия:** загрузка-агрегатор в ту же группу безопасна.
  **Ограничение:** guard сверяет идентичность источника с целью и
  строит ключ по `chat_id` как в конфиге, а маппер входящих — по
  `str(raw.chat_id)` (резолвленный peer); ключи совпадают только если
  чат сконфигурирован числовым id (`-100…`, рекомендованный кейс,
  supergroups §9.4). Для `@username`-конфига source==target guard петлю
  не поймает — задокументировано в докстринге; интеграционный контур
  использует числовые id.

### 2026-06-15 — Ops: restart/catchup через outbox единообразно, `[api.notify]`, busy_timeout для двух писателей, uvicorn-раннер в http-адаптере (T024, M5/C, фаза 4)

- **Контекст:** фаза 4 замкнула группу C — админ-операции (§12.8) +
  командный outbox и роли процессов (§12.9). Несколько развилок:
  как api-процесс инициирует restart/catchup конвейера; куда положить
  цель уведомления о заявке; как пережить двух писателей `app.db` в
  раздельном режиме; куда поместить uvicorn, не затащив FastAPI в ядро.
- **Решения:**
  1. **restart/catchup — всегда через командный outbox**, даже в
     комбинированном режиме (producer и consumer в одном процессе). Один
     механизм и один набор тестов на оба режима (§12.9); admin-ручка
     только ставит команду (`202`), исполняет consumer.
  2. **`restart_pipeline` гасит весь процесс** (взвод `app.restart_event`
     → graceful stop), супервизор (`Restart=always`) поднимает — by
     design §3.2; отдельного «перезапуска без выхода» не вводим.
  3. **Цель уведомления о заявке — секция `[api.notify]`**
     (`account` + `chat_id`); пустая → уведомление выключено. Команда
     `notify` несёт сериализованный `OutboundMessage`; постановка
     неблокирующая (сбой → `notify_failed`, регистрация цела).
  4. **Два писателя `app.db` (раздельный режим) — `PRAGMA
     busy_timeout=5000` + WAL** (§3.1). Записи api-процесса редкие
     (админ-действия), поэтому таймаута достаточно; явный per-write
     ретрай отложен в BACKLOG **T028**.
  5. **uvicorn-раннер — в http-адаптере** (`adapters/http/server.py`,
     extra `web`), импорт uvicorn в шапке модуля; ядро остаётся
     fastapi-free (§14.9). CLI top-импортит раннер — как уже top-импортит
     telegram-адаптер: `angarion` CLI = «батарейки в комплекте».
- **Альтернативы:**
  - restart напрямую в combined (без outbox) — отвергли: раздвоение
    кода/тестов комбинированного и раздельного режимов.
  - Цель уведомления как отдельный pipeline/процессор — отвергли:
    тяжело для «дёрнуть админу сообщение»; `[api.notify]` проще.
  - Второй движок БД (Postgres) ради двух писателей — вне scope M5
    (§16 — SQLite); busy_timeout закрывает редкую запись.
  - Conditional `import uvicorn` в `cli` — отвергли (правило «импорты
    в шапке»); вынесли раннер в отдельный модуль http-адаптера.
- **Последствия:** один путь команд на оба режима; раздельный режим
  работает на одном `app.db` без второго движка; `angarion run
  --with-api`/`--role` требует extra `web` (uvicorn). Зависшие `taken`
  (краш consumer'а между захватом и пометкой) — известный компромисс
  v1 (BACKLOG **T027**, reaper).

### 2026-06-15 — Применение динамики на лету: опрос в начале итерации + событие `settings_changed` для уровня лога (T024, M5/C, фаза 3)

- **Решение:** компоненты с естественным циклом читают
  `RuntimeConfigPort.load()` **в начале итерации** —
  `PipelineWorker._handle` (пауза пайплайна) и `TelegramSender.send`
  (лимиты троттлинга). Уровень лога такого цикла не имеет, поэтому
  применяется по **in-process событию**: `SettingsNotifier`
  (`application/settings.py`) — простой pub/sub; подписчик
  `apply_log_level_on_change` переключает глобальный `wrapper_class`
  structlog (`make_filtering_bound_logger`). Producer события (вызов
  `notify` после `RuntimeConfigPort.save`) подключается в composition
  root в фазе 4 вместе с save-ручкой API.
- **Контекст:** §12.8 / spec FR-4 требует применять динамику без
  перезапуска: «компоненты читают `RuntimeConfigPort` в начале итерации
  … либо по in-process событию `settings_changed` (log level)». Уровень
  лога — глобальное состояние structlog, опрашивать его на каждом
  событии бессмысленно и негде (нет «итерации логирования»).
- **Сдвиг относительно `angarion.log`:** модуль `log.py` декларирует, что
  библиотека **не навязывает** глобальную конфигурацию structlog (право
  приложения — стартовая цепочка процессоров). `apply_log_level` — точечное
  исключение: динамическая фича §12.8 трогает только `wrapper_class`
  (порог фильтрации), стартовую конфигурацию по-прежнему задаёт
  приложение. Опт-ин: подписка `apply_log_level_on_change` навешивается
  в composition root, библиотека сама её не включает.
- **Пауза ≠ потеря:** паузнутый envelope возвращается в хвост
  (`put` строго до `ack` — дубль возможен, потеря нет) + событие
  аналитики `deferred` + короткий sleep (`PAUSE_POLL_SECONDS`) против
  горячего прокручивания накопленной очереди. Зеркалит существующий
  defer-to-tail «раннего» envelope (C-8), но с аудит-событием.
- **Лимиты троттлинга:** sender хранит файловый порог отдельно от
  текущего эффективного; эффективный = override (не-`None` поле
  `DynamicSettings`) либо файл — поэтому сброс override'а возвращает
  файловое значение. `TokenBucket.reconfigure` добирает токены по
  старому темпу, затем подрезает накопленное под новый `capacity` (смена
  лимита не «дарит» всплеск сверх новой ёмкости).
- **Альтернативы:**
  - Опрос уровня лога в цикле worker/sender — отвергли: уровень лога не
    привязан к конкретному компоненту, а structlog-конфиг глобален;
    опрос дублировал бы применение и боролся бы за глобальное состояние.
  - Полный event-bus вместо `RuntimeConfigPort`-опроса для **всех**
    настроек — отвергли как избыточный: пауза и лимиты естественно
    читаются в начале итерации, отдельная подписка усложнила бы их без
    выгоды. Событие оставлено только там, где опрос невозможен.
  - `apply_log_level` в `log.py` — отвергли: противоречит явному
    инварианту модуля «structlog настраивает приложение». Динамический
    applier живёт в application-слое (`settings.py`) как опт-ин фича.
- **Последствия:** динамика паузы и троттлинга — без перезапуска и без
  новых зависимостей; цена — `load()` на каждой итерации worker'а (на
  InMemory дёшево, на SQLite — лёгкий запрос; при росте нагрузки можно
  кэшировать с TTL). `settings_changed` пока без producer'а до фазы 4
  (механизм готов, точка вызова — в save-ручке).

### 2026-06-15 — `CommandOutboxPort` — захват через статус `taken`; at-least-once (T024, M5/C, фаза 2)

- **Решение:** командный outbox (§12.9) с четырьмя статусами —
  `pending` → `taken` → (`done` | `failed`). `take(limit)` атомарно
  захватывает `pending`-команды, переводя их в `taken`
  (`UPDATE ... WHERE status='pending'` + `RETURNING`, проверка по
  rowcount), и возвращает захваченные; `mark_done`/`mark_failed` —
  терминальный переход `taken` → done/failed под тем же статус-guard'ом.
  FIFO — по `created_at` + `rowid`. InMemory захватывает в одной
  корутине без await-точек (событийный цикл её не прерывает) — паритет
  атомарности с SQL.
- **Контекст:** §12.9 требует «семантику at-least-once с защитой по
  статусу — атомарное взятие». Success-критерий спеки §4 явно требует
  тест **«атомарность взятия команды»**: при конкурентном `take` одна
  команда не должна достаться двум consumer'ам. Read-only `take` (как
  `OutboxPort.due`, без смены статуса) этот критерий бы **не прошёл** —
  оба читателя увидели бы одну и ту же `pending`-строку. Поэтому захват
  меняет статус.
- **Отклонение от Key Entities спеки:** §5 перечисляет статусы команды
  как `pending/done/failed` (три). Введён четвёртый — `taken`: без
  не-терминального «захвачено» атомарность взятия невыразима. Список в
  §5 был указательным, критерий §4 («атомарность взятия») — нормативным;
  приоритет у критерия.
- **Альтернативы:**
  - Read-only `take` + guard только в `mark` (паттерн `OutboxPort`) —
    отвергли: не проходит «атомарность взятия» (дубль-захват двумя
    consumer'ами); годится для исходящих (там один `DeliveryWorker`),
    но §12.9 явно про конкуренцию api↔pipeline.
  - Lease/visibility-timeout (как SQS: `taken_at` + reaper, возвращающий
    зависшие `taken` в `pending`) — отложили: для v1 один consumer +
    супервизор (`Restart=always`); восстановление зависших `taken` после
    краха consumer'а — в BACKLOG, не блокирует фазы 3–4. До reaper'а
    at-least-once держится на нормальном пути take→execute→mark.
- **Последствия:** consumer (фаза 4) обязан быть идемпотентным
  (at-least-once). `executed_at` ставится на терминале (`done`/`failed`),
  по нему работает `prune`. Краш между `take` и `mark` оставляет команду
  в `taken` (не переисполняется без reaper'а) — осознанный компромисс v1,
  задача на reaper в BACKLOG.

### 2026-06-15 — `DynamicSettings` — sparse-override; `RuntimeConfigPort` = load/save/reset (T024, M5/C, фаза 1)

- **Решение:** DTO `DynamicSettings` (§12.8) — все поля `X | None`,
  `None` = «нет override'а, действует значение файла»; не-`None` =
  БД-override (приоритет над TOML+env). Порт `RuntimeConfigPort`:
  `load()` (текущие override'ы), `save(patch)` — **частичное** применение
  (только не-`None` поля patch'а меняют сохранённое), `reset(key)` —
  удалить override поля (возврат к файлу). Хранилище — `AppSettingRow`
  (key-value JSON, одна строка на поле), значения через
  `model_dump(mode='json')` (frozenset→list) + `json.dumps`.
- **Контекст:** §12.8 требует «приоритет БД-override над файлом; сброс к
  файлу = удаление override'а» и применение на лету без перезапуска.
  Эффективное значение компонент считает сам: `override ?? file`.
  `paused_pipelines` — чисто динамическое (файлового аналога нет),
  `None` = «ничего не на паузе».
- **Альтернативы:**
  - `save` как полная замена всего набора override'ов — отвергли:
    форма настроек присылала бы все поля целиком, частичные правки
    (pause одного пайплайна) затирали бы прочее. `reset(key)` точнее
    выражает «вернуть к файлу», чем «прислать None».
  - DTO эффективных значений (порт merge'ит с файлом) — отвергли: порт
    не знает файловую конфигурацию; смешение слоёв. Меньше связности —
    порт хранит только override'ы, merge — у потребителя.
- **Последствия:** `RuntimeConfigPort` добавлен в `StorageBundle`
  (storage-backed, как прочие порты); потребители (worker/sender, фаза 3)
  и `/ui/settings` (фаза 4) читают `load()` и сами решают про merge с
  файлом и про метку источника (override = поле не `None`). `updated_by`
  пишется в строку для аудита, наружу пер-поле пока не отдаётся.

### 2026-06-14 — coverage: `concurrency = ["thread", "greenlet"]` для async-SQLAlchemy (T023, M5/B, фаза 3)

- **Решение:** в `[tool.coverage.run]` добавлено `concurrency =
  ["thread", "greenlet"]`.
- **Контекст:** SQLAlchemy async выполняет операции БД в greenlet'е;
  без этой настройки coverage **теряет трассировку** строк, исполняемых
  после `await` к БД, — ложные пропуски в async-ручках web-слоя (ручки
  фазы 3 показывали 61–69% при фактически выполненном коде, что

- **Альтернативы:** `# pragma: no cover` на «непокрытых» строках —
  отвергли как маскировку (код исполняется, виновата трассировка);
  смена `COVERAGE_CORE` (sysmon/ctrace) не помогает (причина —
  greenlet, не ядро).
- **Последствия:** coverage измеряет async-SQLAlchemy честно; порог
  ≥ 90% по-прежнему на реальном покрытии. Требует пакет `greenlet`
  (приходит транзитивно от `sqlalchemy[asyncio]`).

### 2026-06-14 — fastapi-users: свой register-эндпоинт + ручная `require_user`, авторизация на уровне роутеров через `app.state` (T023, M5/B, фаза 2)

- **Решение:** fastapi-users даёт user store, хэш паролей (argon2/pwdlib),
  JWT-стратегию и логин-роутер (`get_auth_router`). Поверх:
  - **регистрация — свой эндпоинт** (`POST /api/v1/auth/register`), не
    дефолтный register-роутер: наша модель — `login` (не email) и заявка
    `is_active=False`/`role=viewer`, дефолтный завязан на email-схему и
    `create_update_dict`. Это же снимает необходимость переопределять
    `BaseUserManager.create` (несовместимость сигнатуры с mypy --strict);
  - **`require_user`/`require_admin` — ручные зависимости**, навешиваются
    на модульные роутеры через `include_router(dependencies=[...])`. Весь
    конфиг аутентификации (секрет, sessionmaker, режим) живёт
    пер-приложение в `app.state.auth` (`AuthState`) и читается в момент
    запроса — поэтому модульные синглтоны (backend, `FastAPIUsers`)
    работают для любого `create_app(...)`; `require_user` переиспользует
    `JWTStrategy.read_token` + менеджер fastapi-users (Bearer для
    `/api/v1`, cookie для `/ui`). `auth="none"` → синтетический локальный
    админ.
  - `AngarionUserDatabase.get_by_email` переопределён на запрос по
    `login` — fastapi-users трактует `login` как идентификатор входа.
- **Контекст:** `FastAPIUsers.current_user` — FastAPI-зависимость,
  построенная из инстанса, требующего секрет в конструкторе; на модульных
  роутерах, общих для всех приложений, это не навесить без пер-app
  пересборки. Чтение конфига из `app.state` в момент запроса развязывает
  модульные роутеры и пер-app конфиг.
- **Альтернативы:**
  - Пер-app пересборка `FastAPIUsers` + хранение `current_user` в
    `app.state` с тонкой обёрткой — отвергли: обёртка над FastAPI-Depends
    вне DI-графа хрупка; ручная `require_user` (декод токена + загрузка
    юзера) прозрачнее и полностью под контролем.
  - Дефолтный register-роутер + `email`-схема + override `create` —
    отвергли: тащит email-валидацию на `login`, конфликт сигнатуры
    `create` с mypy --strict.
- **Последствия:** уровень-роутерная авторизация (§12.7): встроенные
  diagnostics/events и `/ui` закрыты `CurrentUser`; публичны `/health`,
  `/api/v1/auth/*`, статика и webhook-роутеры адаптеров (их аутентифицирует
  платформа). Cookie-вход (`/ui/login`) и одобрение/лимит заявок,
  `/ui/users` — фаза 3.

### 2026-06-14 — `UserRow` ↔ протокол fastapi-users: `TYPE_CHECKING`-аннотации + property-алиасы, без колонок email/superuser/verified (T023, M5/B, фаза 2)

> Продолжение ADR фазы 1 («Схема `UserRow`…»): здесь — *как* модель
> удовлетворяет `UserProtocol` fastapi-users, не заводя его колонок.

- **Решение:** `UserRow` объявляет члены протокола fastapi-users
  (`id`/`hashed_password`/`is_active` и мост-алиасы
  `email`/`is_superuser`/`is_verified`) **плоскими аннотациями в ветке
  `if TYPE_CHECKING:`**, а runtime-определения (Mapped-колонки и
  property-алиасы с сеттерами) — в ветке `else`. `email`=`login`,
  `is_superuser`↔роль `admin`, `is_verified`↔`is_active`.
- **Контекст:** под mypy --strict дескриптор `Mapped[...]` не проходит
  bound-проверку `UserProtocol[Any]` (инвариантность mutable-членов с
  `Any`-параметром) — `SQLAlchemyUserDatabase[UserRow, ...]` краснеет.
  Точно тот же приём (`if TYPE_CHECKING:` с плоскими типами) применяет
  сама fastapi-users в `SQLAlchemyBaseUserTable`.
- **Альтернативы:** наследовать `SQLAlchemyBaseUserTableUUID` — отвергли:
  тащит колонки `email`/`is_superuser`/`is_verified`, дублирующие
  `login`/`role`/`is_active` и противоречащие схеме миграции 0003
  (ADR фазы 1). `# type: ignore` на обобщениях — отвергли (гигиена).
- **Последствия:** storage-слой не импортирует fastapi-users; схема БД
  не меняется (миграция 0003 без новых колонок); property-сеттеры — для
  соответствия mutable-протоколу (в наших потоках не вызываются).

### 2026-06-14 — Схема `UserRow`: `login`/`hashed_password`/`role`-строка, UUID id, без колонок `is_superuser`/`is_verified` (T023, M5/B, фаза 1)

- **Решение:** ORM-сущность `UserRow` (`adapters/storage/orm.py`, миграция
  `0003`) — колонки `id` (нативный `sa.Uuid`, CHAR(32) в SQLite),
  `login` (unique), `hashed_password`, `role` (TEXT `admin`/`viewer`),
  `is_active`, `registered_at`, `approved_at?`, `approved_by?`. Колонок
  fastapi-users `email` / `is_superuser` / `is_verified` в таблице **нет**.
- **Контекст:** §12.7 требует `login` (не email), роли `admin`/`viewer`,
  lifecycle одобрения. fastapi-users-db-sqlalchemy ожидает по протоколу
  атрибуты `email`/`is_superuser`/`is_verified`/`hashed_password`. Схему
  замораживает миграция фазы 1 — выбор колонок надо сделать до фазы 2,
  чтобы не было второй миграции.
- **Альтернативы:**
  - Полный mixin `SQLAlchemyBaseUserTable` (колонки `email`,
    `is_superuser`, `is_verified`) — отвергли: `email`-колонка под логин
    вводит в заблуждение, `is_superuser`/`is_verified` дублируют `role`/
    `is_active` и тащат верификационный поток, который не используем.
    Плюс mixin затащил бы зависимость storage-слоя от fastapi-users.
  - `password_hash` (имя из §12.7) вместо `hashed_password` — отвергли:
    fastapi-users хардкодит атрибут `hashed_password`; синоним ради
    косметики имени — лишний слой. Имя колонки выровнено под библиотеку.
- **Последствия:** в фазе 2 кастомный адаптер user store маппит протокол
  fastapi-users на нашу схему: `email`←`login`, `is_superuser`←
  (`role=="admin"`), `is_verified`←`is_active` — как вычисляемые
  свойства, без колонок. Storage-слой не зависит от fastapi-users
  (id через нативный `sa.Uuid`). Роль хранится строкой — enum `UserRole`
  валидирует на границе auth-слоя (фаза 2).

### 2026-06-14 — Секция `[api]` плоская: `auth` строкой, `secret`/admin-creds из env (T023, M5/B, фаза 1)

- **Решение:** `ApiConfig` (`[api]`) — плоская секция: `host`/`port`,
  `auth: Literal["users","none"]`, `secret`, `jwt_lifetime`,
  `cookie_secure`, `registration_enabled`, `max_pending_registrations`.
  `api.secret` кладётся из env `ANGARION_API__SECRET`; bootstrap-админ —
  из top-level env `ANGARION_ADMIN_LOGIN`/`ANGARION_ADMIN_PASSWORD`
  (поля `admin_login`/`admin_password`). Секреты в TOML не кладутся.
- **Контекст:** §12.7 даёт `auth="users"` строкой и `ANGARION_API__SECRET`
  (= `api.secret`, один `__`). fail-fast по секрету/admin-env и проверка
  bind при `auth="none"` — в bootstrap (фаза 2), не в структурной
  валидации конфига.
- **Альтернативы:** под-таблица `[api.auth]` с `mode=` — отвергли:
  конфликтует с `ANGARION_API__SECRET` (секрет был бы `api.auth.secret`)
  и со строковым `auth="users"` из §12.7. Notify-секция (§12.9) приедет
  отдельным полем в T024 (outbox), а не как `[api.auth.notify]`.
- **Последствия:** `extra="forbid"` — неизвестный ключ `[api]` падает
  fail-fast; T024 добавит поле notify аддитивно. Раннер (uvicorn) для
  `host`/`port` придёт с ролями процессов (T024), конфиг готов раньше.

### 2026-06-14 — Регистрация UI-страниц: дескриптор `Page` + `create_app(pages=…)`, без глобального `register_page` (T022, M5, фаза 3)

- **Решение:** контракт расширения Web UI (§12.6) — иммутабельный
  дескриптор `Page(title, path, router)` + параметр фабрики
  `create_app(deps, pages=[Page(...)])`. Роутер страницы монтируется,
  а `title`/`path` автоматически попадают в навигацию (`env.globals['nav']`,
  собирается в `build_nav`). Функции-реестра `register_page(...)` с
  глобальным мутабельным состоянием **нет**.
- **Контекст:** spec FR-2 называет механизм как `register_page(title,
  path, router)`, но авторитетный код-пример CONCEPT §12.6 —
  `create_app(deps, pages=[Page("Digest", "/ui/digest", ui)])`.
  Навигация и роутеры известны при сборке приложения; держать их в
  явном параметре чище, чем в глобальном списке.
- **Альтернативы:**
  - Глобальный `register_page()` с module-level реестром — отвергли:
    мутабельное глобальное состояние, общее между несколькими `app` в
    одном процессе (тесты, раздельные роли §12.9), — источник
    неожиданных протечек; конфликтует с «один источник истины в
    `app.state`».
  - `register_page(app, ...)` (принимает приложение) — отвергли: ту же
    задачу решает `pages=` без второго способа делать одно и то же.
- **Последствия:** регистрация страниц симметрична `routers=` (JSON) и
  webhook-роутерам — всё через фабрику; навигация детерминирована и
  привязана к конкретному `app`. `register_page` как имя в API не
  публикуется (документация говорит про `pages=[Page(...)]`).

### 2026-06-14 — SSR-шаблоны через `ChoiceLoader` + `app.state.templates` (T022, M5, фаза 3)

- **Решение:** `Jinja2Templates` собирается в `create_app`
  (`build_templates`) и кладётся в `app.state.templates`; встроенный
  UI-роутер достаёт его через DI-зависимость `get_templates(request)`.
  Загрузчик — `ChoiceLoader([FileSystemLoader(user_dir)…,
  FileSystemLoader(builtin)])`: пользовательские каталоги ищутся раньше
  встроенных, так что любой встроенный шаблон (вкл. `angarion/base.html`)
  можно переопределить, а пользовательский шаблон —
  `{% extends "angarion/base.html" %}`. Встроенные шаблоны лежат под
  namespace-префиксом `angarion/`, чтобы не сталкиваться с
  пользовательскими.
- **Контекст:** UI-роутер — module-level `router`, общий для всех
  приложений; набор пользовательских шаблонов/страниц известен только в
  момент `create_app`. Хранить окружение в `app.state` (а не в
  module-global) — единственный способ держать роутер статичным, а
  шаблоны — пер-приложение.
- **Альтернативы:** module-global `Jinja2Templates` — отвергли по той же
  причине, что и глобальный `register_page` (общее мутабельное
  состояние между приложениями).
- **Последствия:** офлайн-ассеты (`pico.min.css`, `htmx.min.js`)
  упакованы в `adapters/http/static/` и отдаются `StaticFiles` по
  `/ui/static/*` (без CDN, §12.6); провенанс/лицензии — в
  `static/README.md`.

### 2026-06-14 — `webhook_router` в `AdapterPlugin` типизирован `Any`, не `APIRouter` (T022, M5)

> **Продолжение решения от 2026-06-11** («`AdapterPlugin` без
> `webhook_router` до M5»): срок настал — поле вводится в M5; здесь
> фиксируется *как* именно, чтобы не нарушить §14.9.

- **Решение:** поле `webhook_router` (§12.11, для
  `push_transport="webhook"`) добавлено в `AdapterPlugin` аддитивно в M5
  с типом `Any` (фактически `fastapi.APIRouter | None`), а не самим
  классом FastAPI. HTTP-адаптер (`angarion.adapters.http.create_app`,
  extra `web`) приводит значение к `APIRouter` через `cast` при
  монтировании.
- **Контекст:** `AdapterPlugin` — pydantic-модель ядра
  (`domain/plugin.py`), модуль без `from __future__ import annotations`
  (аннотации вычисляются в runtime). Типизация поля `APIRouter`
  затащила бы FastAPI в обязательные зависимости ядра — прямое
  нарушение §14.9 / FR-18 (ядро без инфраструктурных зависимостей;
  FastAPI — extra M5). Теперь у контракта есть потребитель (HTTP-адаптер
  §12.5), так что откладывать дальше незачем (снят довод «мёртвый
  контракт» C-1 из ADR 2026-06-11).
- **Альтернативы:**
  - Типизировать `APIRouter` напрямую — отвергли: FastAPI в ядре,
    нарушение §14.9.
  - `TYPE_CHECKING`-импорт + строковая аннотация — не работает: pydantic
    резолвит тип в runtime при построении модели → `NameError`.
  - Оставить поле вне `AdapterPlugin`, собирать роутеры иным каналом —
    отвергли: §12.11 явно помещает `webhook_router` на `AdapterPlugin`,
    это публичный контракт плагина.
- **Последствия:** ядро остаётся `pydantic`-only (FastAPI не
  импортируется ни одним core-модулем). Цена — поле без статической
  типизации в ядре; ответственность за корректность (`APIRouter`)
  лежит на потребителе, который делает `cast`. Тесты `create_app`
  проверяют монтирование реального `APIRouter`.

### 2026-06-14 — Кастомный процессор примера: in-process `register` + `run.py`-лаунчер (T019, M4)

- **Решение:** пример `examples/digest` поставляет stateful-процессор
  одним файлом `processor.py` (импортируемый, тестируемый), а регистрирует
  его не через entry points, а в процессе: тонкий `run.py` вызывает
  `application.processors.register(DIGEST)` и запускает штатный run-loop
  библиотеки (`cli.cmd_run`). Каталоги примеров объявлены
  ruff `namespace-packages = ["examples/digest"]` — подавляет ложный
  INP001 на одиночных скриптах без `__init__.py`, не расширяя `ignore`.
- **Контекст:** `angarion run` находит процессоры только через entry
  points `angarion.processors` — config-хука «импортируй мой модуль» нет
  (близко к T021). Кастомный процессор примера, не оформленный пакетом,
  иначе не подключить. ruff `select=ALL` без exclude для `examples/`
  ловит INP001 на `examples/digest/*.py`.
- **Альтернативы:**
  - Пример как устанавливаемый мини-пакет с entry point + `uv pip install
    -e` в `run.sh` — самый «штатный» путь дистрибуции стороннего
    процессора, но добавляет `pyproject.toml`/`src`-обвязку и install-шаг,
    что заслоняет урок «как написать процессор». Отвергли для примера
    (путь через entry point всё равно показан сниппетом в README).
  - Exclude `examples/` из ruff — отвергли: примеры — образцовый
    user-facing код, его качество хотим линтить.
  - Per-file-ignore INP001 — отвергли: `namespace-packages` семантически
    точнее (каталог намеренно не пакет) и не трогает `ignore`-секцию.
- **Последствия:** примеры с кастомным кодом запускаются через свой
  `run.py` (а не голый `angarion run`); README показывает и
  entry-point-путь для упакованного процессора. При новых примерах с
  одиночными скриптами — дополнять `namespace-packages`. Решение
  Владимира 2026-06-14.

### 2026-06-14 — `jinja2` — core-зависимость (`template` — встроенный v1) (T007, M4)

- **Решение:** `jinja2` добавлен в основные `dependencies`, а не в extra.
  Процессор `template` регистрируется eager в `application/processors.py`
  рядом с `passthrough` и всегда доступен; LLM-промпты используют тот же
  Jinja2-движок (`application/templating.py`). Под extra `angarion[llm]`
  уходит только `httpx` (+ `tenacity`) — реальный сетевой I/O.
- **Контекст:** §10.2 числит `template` встроенным процессором v1 (как
  `passthrough`). Правило «импорты только в шапке» даёт жёсткое следствие:
  если `template` живёт в eager-загружаемом `processors.py` и импортирует
  `jinja2` сверху — `jinja2` де-факто становится обязательным. §9 ТЗ
  изначально относил `Jinja2` только к extra `[api]`.
- **Альтернативы:**
  - Оба процессора (`template`+`llm`) под единым extra `[llm]`
    (`jinja2`+`httpx`), регистрация через entry points — отвергли:
    «чисто template»-сценарий тянул бы `httpx`, а extra с именем `llm`
    для не-LLM процессора вводит в заблуждение.
  - Два extra (`[template]`=jinja2, `[llm]`=jinja2+httpx) — отвергли:
    вводит extra `[template]`, которого нет в §9; гранулярность не стоит
    лишней оси конфигурации.
- **Последствия:** `template` доступен из коробки, как и `passthrough`;
  consistency с «встроенный v1». Отступление от §9 (там `jinja2` был
  только в `[api]`) — осознанное, подтверждено Владимиром 2026-06-14.
  `jinja2` — pure-python рендеринг, не инфраструктура в смысле §14.9
  (нет связи с БД/сетью/платформой), поэтому в core он уместен.

### 2026-06-14 — HTTP-клиент LLM: `httpx`, не `aiohttp` (T007, M4)

- **Решение:** OpenAI-совместимый вызов `llm`-процессора идёт через
  `httpx.AsyncClient`.
- **Контекст:** нужен async HTTP-клиент под `/v1/chat/completions` с
  требованиями проекта: тесты без сети (CI), `mypy --strict`, явные
  таймауты.
- **Альтернативы:** `aiohttp` — отвергли. Его сильные стороны (высокий
  throughput, websockets, встроенный сервер, тонкий пул под массовую
  конкурентность) для нас не применимы: worker конкурентен = 1 и
  событийный (§6.3), один LLM-вызов за раз — throughput не фактор. У
  `httpx` решающие для проекта плюсы: `MockTransport` → unit-тесты `llm`
  без сети (FR «Тестируемость»); хорошая типизация под `mypy --strict`
  (W3); `httpx` уже придёт для ASGI-тестов ручек (§12.5) — один клиент на
  проект; явные granular-таймауты (W5, `timeout_s`). `aiohttp` потребовал
  бы `aioresponses` либо мок только на нашей тонкой границе.
- **Последствия:** единый HTTP-клиент во всём проекте; «CI без сети»
  идиоматичен. При появлении высоконагруженных сценариев (вне текущей
  модели worker=1) — пересмотреть.

### 2026-06-14 — `llm`-процессор: тонкая HTTP-граница + ретраи в процессоре (T007, M4)

- **Решение:** вся логика `llm` живёт над узкой границей
  `LlmHttpClientPort` (метод `post_chat`); реальная обёртка
  `HttpxLlmClient` бритвенно-тонкая, сетевые ошибки нормализованы в
  httpx-free `LlmTransportError`. Ретраи (сеть/`5xx`/`429`, `tenacity`,
  exp-backoff, `Retry-After` с потолком `timeout_s`; `4xx≠429` без
  ретраев → `ProcessingError`) живут **в процессоре**, не в обёртке.
  `processor_config` (`LlmProcessorConfig`) валидируется лениво и
  кэшируется по имени пайплайна (W1).
- **Контекст:** §10.1 контракт `ProcessorPort` не несёт `config_model`,
  bootstrap не знает, какой моделью валидировать `processor_config` на
  старте (§11 fail-fast). Нужен и тестируемый без сети HTTP-вызов

  - Прямой вызов `httpx` из процессора (без порта) — отвергли: ломает

- **Последствия:** `llm` тестируется на fake-границе и `MockTransport`

  (не на старте) — осознанный компромисс W1, до реализации T021.
  Повторный вызов под at-least-once расходует токены/даёт иной ответ
  (W2) — дублирующую доставку гасит outbox/`mark_delivered` (§7.3).

    отвергли: StateStore семантически про состояние stateful-процессоров

    `SessionStorePort` чище и не перегружает контракт KV.
  - Telegram-адаптер владеет своей ORM-таблицей/миграцией (как сторонний
    storage-бэкенд §12.11) — отвергли: telegram — адаптер платформы, не
    storage-бэкенд; схема живёт в встроенном storage-адаптере.
- **Последствия:** +1 порт и контрактный набор, +1 ORM-таблица, миграция
  `0002`; крипто-зависимость (`cryptography`) в extra `angarion[telegram]`;

  иначе fail-fast). Бэкап-гайд (§17.6, M3-доки) обновляется: учётные данные
  аккаунтов теперь внутри `app.db`, ключ шифрования бэкапится **отдельно**
  от БД (иначе бэкап бесполезен/опасен). Потеря/ротация ключа = re-login
  (`angarion login`). Ограничение §12.1 «один процесс владеет сессией»
  сохраняется — оно про MTProto-состояние в памяти, не про форму хранения.

### 2026-06-13 — Ревизия tgcf перед M3: заимствований кода нет, берём приёмы Telethon (T004)

- **Решение:** по итогам ревизии исходников

### 2026-06-12 — Отметка дедупа после fan-out: `seen()` + перенос `mark_inbound` (T003, A-11)

- **Решение:** `DedupStorePort` получает аддитивный метод `seen()`
  (чистая проверка без записи); `IngestService` проверяет `seen()` на
  входе, а отметку `mark_inbound()` пишет **строго после** постановки
  всех envelope в очередь (и на unrouted-ветке).
- **Контекст:** при проектировании kill-теста M2 (FR-12) найдено
  крэш-окно: отметка дедупа коммитилась в `app.db` до записи envelope
  в `queue.db`; kill -9 между ними делал событие невосстановимым —
  ре-эмит (catch-up §9) гасился как «дубль». Нарушение сквозного
  at-least-once (§7.1 ТЗ) и acceptance SC-2. Формально фикс —
  отступление от FR-13 («M2 не меняет домен и application»),
  одобрен Владимиром 2026-06-12.
- **Альтернативы:**
  - Оставить порядок, признать окно ограничением M2 (BACKLOG на M3) —
    отвергнуто: рандомный SIGKILL kill-теста попадает в окно (~мс на
    событие), тест флейковал бы по вине конвейера, SC-2 не выполнен.
  - `mark_inbound` в конце без проверки на входе (без изменения
    порта) — отвергнуто: реальные дубли (массовый кейс catch-up)
    фанаутились бы в очередь и гонялись через worker впустую.
  - Транзакционно связать отметку и постановку — невозможно:
    `queue.db` (persist-queue) и `app.db` — раздельные базы по
    построению (§12.3).
- **Последствия:** kill в новом окне «put → отметка» даёт при
  ре-эмите повторную постановку envelope: реестр переписывается
  идемпотентно (`unchanged`), дубль обработки гасит outbox
  (insert-if-absent, C-9) — дубль вместо потери, что и требует
  at-least-once. Каждое событие делает два обращения к dedup-порту
  (seen + mark) — приемлемый оверхед. Контракт `DedupStoreContract`
  дополнен наборами `seen()`; сторонние реализации порта обязаны
  добавить метод (мажорных потребителей пока нет).

- **Решение:** контрактные наборы тестов портов — публичный пакет

### 2026-06-11 — Transactional outbox для исходящих вместо «mark до send» (T002, C-9)

- **Решение:** обработка и доставка разделены: `PipelineWorker`
  фиксирует outbound в `OutboxPort` (insert-if-absent по
  `idempotency_key`) строго до `ack`; отдельный `DeliveryWorker`
  доставляет pending-записи с собственным retry/backoff, после
  `max_retries` — терминальный статус `failed` (аналог DLQ для
  исходящих, разбор ручной). `mark_delivered` удалён из
  `DedupStorePort`; выходная идемпотентность — первичный ключ outbox.
- **Контекст:** дословный §6.3 ТЗ (`mark_delivered` до `send`) при
  сбое отправки терял сообщение: оно уже помечено доставленным, но не
  отправлено. ТЗ не догма — решение Владимира 2026-06-11.
- **Альтернативы:**
  - Read-only `is_delivered` + порядок «send → mark» — чинит потерю,
    но ретрай доставки ре-выполняет процессор (дорого для
    LLM-процессоров M4).
  - Acquire/confirm с lease — нужен только при параллельных worker'ах
    (§17.8), не M1.
  - Только tenacity внутри sender'а (M3) — mitigation, не fix:
    исчерпание ретраев всё равно теряло сообщение.
- **Последствия:** сбой отправки не теряет сообщение; ретраи
  per-message и не трогают процессор; готовая точка персистентности
  (M2) и мониторинга/requeue (M5). Остаточное окно «send выполнен,
  mark_sent не записан» при падении процесса даёт дубль, не потерю —
  допустимо at-least-once §7.1.

### 2026-06-11 — Retry через `not_before` в envelope + defer-to-tail (T002, C-8)

- **Решение:** экспоненциальный retry обработки реализован полем
  `QueueEnvelope.not_before`: ретрай кладётся
  `put(attempt+1, not_before=now+backoff)` строго до `ack` исходного;
  worker, получив «ранний» envelope, возвращает его в хвост
  (`put` + `ack`) с коротким sleep (cap 1 с). Backoff:
  `min(base * 2^attempt, cap)`, default 1 с / 60 с, `max_retries=5`,
  секция конфига `[worker]`.
- **Контекст:** ТЗ задаёт только `max_retries=5`; механизм задержки
  не специфицирован, а порт очереди должен пережить персистентные
  реализации M2 без изменений.
- **Альтернативы:**
  - In-process таймер (sleep между `ack` и повторным `put`) — окно
    потери ретрая при падении процесса, ломает at-least-once в M2.
  - Параметр `delay` в контракте `put()` — усложняет каждый адаптер
    очереди (у persist-queue нативной задержки нет) ради того же
    результата.
- **Последствия:** порядок крэш-безопасен (падение между `put` и
  `ack` даёт дубль, не потерю); рестарт с персистентной очередью M2
  переживается без правок порта; механика паузы §12.8 (M5) ляжет на
  тот же `not_before`. Цена — «ранние» envelope циркулируют через
  хвост очереди (с sleep-демпфером против горячего цикла).

### 2026-06-11 — Нормализация текста для content_hash: NFC + переводы строк (T002, A-4)

- **Решение:** `normalize_and_hash(text)` = Unicode-нормализация NFC →
  `\r\n` и одиночный `\r` → `\n` → `sha256(utf-8).hexdigest()`.
  Больше ничего. Правила — публичный контракт, зафиксированы
  golden-тестами; изменение — только мажорная версия (§7.2).
- **Контекст:** хэш входит в dedup-ключ EDITED-событий; ТЗ объявляет
  правила публичным контрактом, но не определяет их — первое же
  решение фиксируется надолго.
- **Альтернативы:** агрессивная нормализация (trim / lower /
  схлопывание пробелов) — отвергнута: склеивала бы содержательно
  разные версии текста (правка регистра или пробелов — реальная
  правка); полное отсутствие нормализации — отвергнуто: NFC-вариации
  и платформенные переводы строк дали бы ложные «новые версии» одного
  текста между live и catch-up.
- **Последствия:** дедуп стабилен между платформами и путями доставки
  события; семантически незначимые вариации Unicode/EOL не плодят
  версий. Содержательно одинаковые тексты с разными пробелами считаются
  разными версиями — осознанно.

### 2026-06-11 — `AdapterPlugin` без `webhook_router` до M5 (T002, A-1)

- **Решение:** поле `webhook_router: APIRouter | None` (§12.11 ТЗ) в
  контракт `AdapterPlugin` M1 не входит; добавится аддитивно в M5
  (минорная версия, санкционированная эволюция §17.8). Ветка
  деградации `push_transport="webhook"` соответственно не реализуется.
- **Контекст:** поле типизировано классом FastAPI — это тянет FastAPI
  в обязательные зависимости ядра, что противоречит §14.9 / FR-18
  (ядро без инфраструктурных зависимостей; FastAPI — extra M5).
- **Альтернативы:** типизировать поле `Any` — отвергли: контракт без
  потребителя (HTTP-адаптера нет до M5) — мёртвый контракт, принцип
  C-1.
- **Последствия:** ядро M1 — только pydantic, pydantic-settings,
  structlog; webhook-адаптерам до M5 регистрироваться некуда
  (платформ с webhook-транспортом в плане до M5 нет).

### 2026-06-11 — Временные api_id/api_hash от Telegram Desktop для интеграционного контура

> **Частично заменено решением от 2026-06-13** (гейт «собственные ключи
> до начала M3» снят; см. ADR 2026-06-13 «Снятие гейта собственных
> api-ключей перед M3»). Остальная часть решения (использование ключей
> TDesktop api_id 2040 для интеграционного контура) — в силе.

- **Решение:** интеграционные тесты (T014) запускаются на публичных
  ключах Telegram Desktop (api_id 2040 — открытый исходник tdesktop);
  собственные ключи — обязательны до начала M3 (задача T015).
- **Контекст:** my.telegram.org стабильно возвращает «ERROR» на
  «Create new application». Из РФ сайт без VPN недоступен (блокировка
  на стороне провайдеров), с VPN создание приложения отклоняется;
  выход через российский VPS невозможен по той же причине.
- **Альтернативы:**
  - Ждать починки my.telegram.org — отвергли как блокер всей работы
    с интеграционным контуром; форму продолжаем пробовать (T015).
  - Ключи других официальных клиентов — без преимуществ перед TDesktop.
- **Последствия:** смоук-тест работает уже сейчас; формальное
  отступление от ToS API и чуть повышенное внимание антиспама —
  приемлемо для низкочастотного теста на личном аккаунте, неприемлемо
  для боевого пайплайна (отсюда жёсткий дедлайн T015 «до M3»).
  Замена ключей — правка `.secrets` + переавторизация скриптом.
